# 09. 실무 코딩스타일 — 작성한 HTML을 다시 읽는 순서

[HTML 목차](README.md) · [종합실습](10_HTML_종합실습.md)

이 장은 강사님·내 `03_a.html`, `05_table.html`, `07_form.html` 등에서 배운 태그로 문서를 작성한 뒤 **내용과 제출 결과를 점검하는 복습**이다. 아래 점검 코드는 원본 발췌가 아니라 **수업 범위를 묶어 새로 작성한 예시**다. 기본 오류의 원본 비교는 각 본문 장에 남겨 두었다.

## 1. 문서의 목적을 제목과 구조로 드러내기

`title`은 브라우저 탭에, `h1`은 본문에 나타난다. 둘 중 하나만 작성한 상태를 피하고, 목록은 항목을 `li`로 묶어 읽는다. [문서 구조](01_HTML_기초와_문서구조.md)와 [목록](04_HTML_목록태그.md)에서 원본을 다시 확인할 수 있다.

```html
<!-- 수업 내용으로 재구성한 점검 예시 -->
<title>수업 신청</title>
<h1>수업 신청 안내</h1>
<h2>준비물</h2>
<ul><li>필기도구</li><li>수업 자료</li></ul>
```

## 2. 화면에 보이는 말과 제출되는 값을 따로 확인하기

폼에서는 `label`의 글자만 보고 제출값을 짐작하지 않는다. `name`이 쿼리의 이름이 되고 `value`가 값이 된다. 다음 예시는 선택 후 GET으로 제출할 때 `topic=html`이 된다. [내 폼 코드와 강사님 코드 비교](07_HTML_폼과_입력요소.md) 및 [GET·POST](07-02_HTML_폼_전송과_GET_POST.md)를 먼저 읽는다.

```html
<!-- 수업 내용으로 재구성한 점검 예시 -->
<form method="get">
  <label><input type="checkbox" name="topic" value="html" checked>HTML 복습</label>
  <button type="submit">신청</button>
</form>
```

## 3. 제출 전후 점검하기

1. 링크의 `href`와 이동 대상 `id`가 맞는지 확인한다.
2. 표의 제목 행은 `th`, 데이터 행은 `td`로 구분하고 닫기 태그를 확인한다.
3. 이미지의 `src` 경로와 `alt` 문구를 확인한다.
4. 폼의 `name`, `value`, `checked`, `selected`를 보고 실제 전송값을 예상한 뒤 브라우저 주소에서 확인한다.

이 순서에 해당하는 원본 사례는 [링크](03_HTML_링크와_경로.md), [표](05_HTML_테이블.md), [이미지](06_HTML_이미지와_미디어.md)에 있다. 태그를 더 많이 쓰는 것이 목표가 아니라 **현재 문서의 동작을 설명할 수 있는가**가 점검 기준이다.

## 추가로 알면 좋은 것

이하의 내용은 **수업 원본에서 확인된 필수 진도가 아닌 추가 학습**이다. 위의 기본 설명을 이해한 뒤 필요할 때 읽는다.

<a id="extra-03-2"></a>

### 2. 작성 규칙은 읽는 목적을 위해 정한다

들여쓰기·속성 줄 나누기·이름 붙이기는 코드를 다시 읽기 위한 약속이다. 한 프로젝트 안에서 일관되게 적용하되, 띄어쓰기 모양만으로 동작이 달라진다고 설명하지 않는다.

```html
<input
    type="text"
    id="student-name"
    name="student_name"
    value="학습자"
>
```

이것은 추가 학습용 재구성이다. `id`와 `name`을 같은 문자열로 만드는 것이 필수는 아니다. 각각의 연결 대상과 제출 계약을 알아보기 쉽게 정한다. 수업 원본 이름을 이 규칙에 맞추어 바꾼 뒤 “원본”이라고 표시하지 않는다.

클래스 이름을 `card__title` 같은 형식으로 정하는 규칙, 폴더 구조를 역할별로 나누는 방식 등은 협업 설계의 선택이다. 그 이름을 붙이기만 하면 스타일·기능이 생기는 것은 아니다. 이미지 파일명을 바꾸면 이를 참조하는 `src`·링크도 함께 수정한다.

<a id="extra-03-3"></a>

### 3. 무엇을 검증하는지 나누어 보기

| 확인 대상 | 확인할 증거 | 그것만으로는 알 수 없는 것 |
| --- | --- | --- |
| 문법·중첩 | 소스와 검사 도구의 오류 위치 | 화면의 목적과 내용 품질 |
| 실제 구조 | 브라우저가 해석한 요소 관계 | 다른 브라우저의 모든 동작 |
| 링크·자원 | 요청한 주소와 응답 | 앞으로도 외부 자원이 항상 유지되는지 |
| 폼 | 요청 방식·전송 항목·서버 응답 | 실제 DB 저장까지 성공했는지 |
| 키보드 사용 | 이동 순서·활성화 가능 여부 | 모든 보조 기술에서 같은 경험인지 |
| 접근 가능한 이름·역할·상태 | 해당 트리와 실제 보조 기술 사용 | 속성을 넣었다는 사실만으로 전체 접근성이 완성되는지 |

브라우저의 개발자도구, HTML 검사 도구, 키보드, 보조 기술은 서로 다른 질문에 답한다. 이번 HTML 개편에서 실제로 검사한 범위는 [검증 기록](../편집기록/01_HTML_최종_검증기록.md)에 적었다. 검사하지 않은 항목까지 통과했다고 쓰지 않는다.

<a id="extra-03-4"></a>

### 4. 기존 실무 확장 과제를 읽는 순서

- 먼저 콘텐츠와 이동·입력의 목적을 정한다.
- 시맨틱 영역과 제목 구조를 검토한다.
- 필요한 경우 입력 묶음·추가 검증·도움말을 붙인다.
- CSS 배치와 JavaScript 동작은 해당 과목 지식으로 별도 구현한다.
- 마지막으로 키보드·보조 기술·서버 응답을 검토한다.

메뉴 토글, 다크 모드, 오류 메시지 자동 연결, `aria-live` 상태 알림, 구조화 데이터, 검색 최적화 전체 설계는 이 HTML 기초의 기본 과제가 아니다. 필요한 기능부터 별도로 학습한다. 입력 검증이나 보안이 HTML 속성 몇 개만으로 완성된다는 표현도 피한다.

<a id="extra-03-5"></a>

### 선택 복습

“화면이 잘 보이고 HTML 검사 오류가 없으니 제출값도 올바르다”라는 결론은 충분할까?

<details>
<summary>해설</summary>

충분하지 않다. name 누락·비활성 상태·선택값 때문에 제출 내용이 의도와 다를 수 있다. 무엇을 확인하려는지에 맞는 증거를 따로 본다.

</details>
