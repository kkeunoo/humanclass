# HTML 실무 코딩스타일 — 구조와 동작의 의도를 읽기 쉽게 남기기

[HTML 목차](README.md) · [종합실습](10_HTML_종합실습.md)

들여쓰기만 맞는다고 읽기 좋은 코드가 완성되지는 않는다. 링크는 어디로 가는지, 표는 무엇을 설명하는지, 입력은 어떤 이름으로 제출되는지가 보여야 한다. 이 장은 실제 수업에서 찾은 차이를 바탕으로 **작성한 문서를 다시 검토하는 순서**를 연습한다.

## 1. 이번 장에서 배울 것

수업에서 배운 태그로 문서를 만든 뒤 **구조·경로·자료의 이름과 값·사용자 조작**을 점검한다. 아래 예제는 실제 수업 원본 과제가 아닌 **새로 구성한 복습**이며, 별도 실무 프로젝트를 배웠다는 뜻이 아니다.

| 조건 | 내용 |
| --- | --- |
| 앞선 학습 | 문서 구조부터 GET·POST까지 기본 8장 |
| 근거 | 내·강사님 03_a.html·04_ul.html·05_table.html·07_form.html |
| 실행 파일 | [실습/09_작성스타일_복습.html](실습/09_작성스타일_복습.html) |
| 필요한 환경 | 브라우저; 제출은 HTTP 미리보기에서 확인 |
| 새 예제의 범위 | 배운 구조·입력·선택만 사용; CSS·JS·서버 저장 없음 |

원본과 개선안은 구별한다. 원본을 새 형식으로 고친 다음 그것을 당시 작성한 코드라고 표시하지 않는다.

## 2. 개념부터 이해하기

### 일관성은 읽는 목적을 돕는 약속

속성을 줄마다 나누면 긴 src·id·name·value를 비교하기 쉽다. 하지만 줄바꿈 형식만으로 프로그램 동작이 바뀌는 것은 아니다. **표현상의 약속과 실제 동작 규칙을 나눠** 설명한다.

| 점검 대상 | 묻는 질문 | 기준 |
| --- | --- | --- |
| 구조 | 내용의 역할이 태그와 맞는가? | 제목·목록·표·폼의 의미 |
| 이름 | 연결할 대상이 분명한가? | id·for·name의 각각의 역할 |
| 동작 | 클릭·선택 뒤 무엇이 일어나는가? | href·type·method·action |
| 자료 | 실제로 보낼 값은 무엇인가? | 현재값·선택·활성 상태 |
| 형식 | 다음 사람이 빠르게 읽을 수 있는가? | 일관된 들여쓰기·줄 나누기 |

예를 들어 id와 name을 같은 문자열로 만드는 규칙이 필수는 아니다. for는 id를 참조하고, 서버는 제출 이름을 읽는다. 이름을 정할 때 두 계약을 알아볼 수 있게 하는 것이 중요하다.

## 3. 작은 예제와 결과

다음은 **새로 만든 검토 대상 코드 조각**이다. ‘입력값을 제출하고 싶고, 일반 버튼은 제출하지 않게 하려는 목적’이라고 가정한다.

```html
<form>
    <input id="student-name" value="student">
    <button>일반 버튼</button>
</form>
```

입력의 id만으로 제출 이름이 생기지 않으며, 이 수업의 일반 form에서 type 없는 button은 제출 버튼으로 동작한다. 보기 좋게 줄을 나눠도 목적과 동작이 어긋나는 부분은 그대로다.

**개선 예시 · 새 독립 실행 문서.** [09_작성스타일_복습.html](실습/09_작성스타일_복습.html)의 전체 내용이다.

```html
<!DOCTYPE html>
<html lang="ko">
<head>
    <meta charset="UTF-8">
    <title>HTML 작성 검토</title>
</head>
<body>
    <h1>입력과 제출의 의도</h1>
    <form action="09_작성스타일_복습.html" method="get">
        <p>
            <label for="student-name">이름</label>
            <input
                type="text"
                id="student-name"
                name="learner"
                value="student"
            >
        </p>
        <p><label><input type="checkbox" name="topic" value="html" checked>HTML 복습</label></p>
        <button type="button">일반 버튼</button>
        <button type="submit">전송 확인</button>
    </form>
</body>
</html>
```

초기 상태의 예상 제출 항목은 `learner=student&topic=html`이다. 일반 버튼에는 별도 기능을 연결하지 않아 눌러도 기본 제출은 하지 않는다. 전송 확인 버튼은 폼을 제출한다. id와 name이 다른 것은 오류가 아니라 서로 다른 역할을 드러낸 선택이다.

**한 가지 변경 실험:** topic 체크박스의 선택만 해제하면 제출 항목에서 topic=html이 빠진다. label 글자를 바꾸는 실험과 name·value를 바꾸는 실험은 각각 다른 목적이므로 한 번에 하나씩 바꿔 확인한다.

## 4. 내 코드에서 확인한 선택

원본 발췌는 각 개념 장에 정확한 구간으로 남겨 두었다. 여기서는 새 코드인 것처럼 다시 인용하지 않고 **검토 습관으로 옮길 수 있는 효과**를 읽는다.

| 내 원본에서 확인한 것 | 잘한 점 또는 보완할 점 | 대표 설명 |
| --- | --- | --- |
| 아래 이동에 href와 bottom ID 연결 | 목적지까지 연결을 완성 | [링크 장](03_HTML_링크와_경로.md#fragment) |
| 중첩 목록의 부모 이름 작성 | 하위 항목의 소속이 분명 | [목록 장](04_HTML_목록태그.md#nested) |
| 체크박스 마지막 value 5 명시 | 선택값 구별이 분명 | [폼 장](07_HTML_폼과_입력요소.md#choice) |
| 표의 summary와 th 닫기 | 요소 용도·문법 교정 필요 | [표 장](05_HTML_테이블.md#review) |

같은 파일 안에서도 좋은 선택과 고칠 부분이 함께 있다. 전체를 ‘좋은 코드’ 또는 ‘나쁜 코드’로만 평가하면 어떤 습관을 이어 갈지 배우기 어렵다.

## 5. 다른 파일과 연결하기

HTML을 옮기거나 파일명을 바꾸면 src·href·action이 가리키는 대상도 다시 확인한다. 화면 하나의 태그가 맞아도 연결된 파일이 없으면 실행 결과는 달라진다.

| 참조 | 점검할 것 |
| --- | --- |
| href | 현재 위치에서 목적지 파일·ID까지 이어지는가? |
| src | 이미지·미디어 자원이 실제로 있는가? |
| action | 요청을 받을 문서·서버가 무엇인가? |
| for | 같은 문서 안의 맞는 id에 연결되는가? |

새 예제의 action은 자기 문서다. 값을 저장하는 서버 함수를 import한 구조가 아니므로, 같은 HTML이 다시 표시된 것과 저장 성공을 구별한다.

## 6. 코드를 검토하는 순서

1. 문서의 목적을 제목과 내용으로 설명한다.
2. 요소의 구조·닫기·중첩을 확인한다.
3. 링크·자원·라벨이 실제 대상을 가리키는지 본다.
4. 현재 상태에서 보낼 이름과 값을 예상한다.
5. 확인 방법에 맞춰 관찰한 결과를 기록한다.

| 발견한 것 | 평가 종류 | 조치 |
| --- | --- | --- |
| 잘못된 닫기 태그 | 문법 오류 | 시작 요소와 맞춰 수정 |
| name 누락 | 요구사항에 따라 다름 | 제출할 항목이면 명시; 비교 실험이면 의도 기록 |
| border로 경계 표시 | 수업용 관찰 | 현대 표시 설계는 CSS로 연결 |
| 속성 여러 줄 또는 한 줄 | 형식 선택 | 프로젝트 안의 읽기 일관성 유지 |
| 실제 동작 없는 일반 버튼 | 목적 확인 | 버튼 역할 실험인지 기능 미구현인지 표시 |

이 기준은 ‘다른 형식은 모두 틀리다’는 규칙이 아니다. 정확성·의도·수업 범위·표현 선택을 각각 판단한다.

## 7. 강사님 코드에서 배울 점

이미지 속성을 여러 줄에 나누는 방식과 title 안에 필요한 텍스트만 두는 구조는 강사님 코드에서 참고했다. 한편 문서 안 아래 이동은 내 코드가 연결을 더 완성했고, summary를 표에 넣은 것은 양쪽 모두 교정했다.

이 장에서 원본 블록을 다시 길게 붙이지 않는 이유는 비교를 생략해서가 아니라, **실제 차이와 효과를 앞선 장에서 확인한 뒤 작성 습관으로 옮기는 단계**이기 때문이다. 헷갈리면 표의 대표 장으로 돌아가 정확한 코드를 본다.

## 8. 결과와 확인 방법

| 확인하려는 질문 | 필요한 증거 | 그것만으로 알 수 없는 것 |
| --- | --- | --- |
| 구조가 맞는가? | 소스·검사 도구의 구조 오류 위치 | 화면의 내용 품질 |
| 링크가 맞는가? | 실제 대상 경로·파일·응답 | 외부 자원의 장기 유지 |
| 이름표가 연결됐는가? | for·id와 실제 조작 | 모든 보조 기술의 경험 |
| 제출값이 맞는가? | 항목 구성과 실제 요청 데이터 | DB 저장 성공 |
| 화면이 읽기 좋은가? | 실제 화면과 사용자 흐름 | 소스 문법이 모두 올바른지 |

새 예제는 구조·label 연결·초기 제출 항목을 정적으로 확인한다. 브라우저·키보드·보조 기술·실제 서버는 서로 다른 확인 도구이므로 실행하지 않은 검사까지 통과했다고 쓰지 않는다.

## 9. 추가로 알면 좋은 것

<a id="extra-03-2"></a>

> 💡 **TIP · 수업 범위 밖:** 클래스 이름을 일정한 형식으로 정하는 협업 규칙, 자동 포매터·HTML 검증 도구는 추가 학습이다. 규칙 이름을 붙인다고 화면 동작이 생기는 것은 아니며, 이름 변경 뒤의 참조도 함께 수정해야 한다.

<a id="extra-03-4"></a>

> 💡 **TIP · 수업 범위 밖:** 메뉴 토글·다크 모드·상태 알림·구조화 데이터·검색 최적화 전체 설계는 현재 HTML 기초 과제의 필수 구현이 아니다. 먼저 구조와 입력·이동 목적을 정하고, 필요한 CSS·JavaScript·서버 기능을 이후 단원에서 연결한다.

> 📚 **출처 · 본문 설명 확인:** 기본 문법은 [MDN — HTML syntax](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/Basic_HTML_syntax), 폼 제출·버튼·이름 규칙은 [HTML 표준 — 폼 제어](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html)와 [폼 요소](https://html.spec.whatwg.org/multipage/form-elements.html)로 확인했다. 확인일: 2026-10-28. 형식 예제와 이 장의 점검 순서는 새로 구성했다.

## 10. 복습과 다음 학습

1. 새 예제에서 name learner를 student로 바꾸면 라벨 연결도 반드시 고쳐야 할까?
2. 구조 검사에 오류가 없으면 제출값도 요구사항과 맞는다고 결론 내릴 수 있을까?
3. 일반 버튼이 전송되는 실수를 막으려면 어느 속성을 명시할까?

<details>
<summary>풀이</summary>

라벨은 id에 연결돼 있어 name만 바꾸는 경우 for·id가 자동으로 바뀔 필요는 없다. 다만 받는 쪽이 읽을 제출 이름은 달라진다. 구조 검사와 데이터 요구사항은 별도이므로 제출 항목도 확인한다. 일반 버튼은 type="button"으로 의도를 명시한다.

</details>
