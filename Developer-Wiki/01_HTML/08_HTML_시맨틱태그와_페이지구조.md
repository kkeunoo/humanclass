# 시맨틱 페이지 구조 — 전체가 추가 학습인 선택 부록

[HTML 목차](README.md) · [기본 종합실습](10_HTML_종합실습.md)

> 💡 **TIP · 이 장 전체가 수업 범위 밖 선택 학습:** 이 장의 header·nav·main 등 페이지 영역 구성은 비교한 HTML 기초 수업 파일에서 확인된 필수 진도가 아니다. 코드와 설명은 책을 위한 새 예제이며, 기본 장별 문제를 풀기 위한 선행 조건으로 요구하지 않는다.

## 1. 이번 장에서 배울 것

기본 제목·목록·표·폼은 각각 내용의 역할을 나타낸다. 시맨틱 페이지 구조는 그 생각을 **페이지 전체의 영역**으로 넓힌다. 소개·주요 탐색·중심 내용·관련 안내를 어떤 역할의 묶음으로 볼지 정한다.

| 조건 | 내용 |
| --- | --- |
| 앞선 이해 | h1~h3, p, a와 문서 안 ID 이동 |
| 실행 예제 | [실습/08_시맨틱_추가복습.html](실습/08_시맨틱_추가복습.html) |
| 실행 환경 | 브라우저로 파일 열기, 외부 파일·서버 불필요 |
| 기본 모양 | CSS 없음; 영역이 자동으로 가로 배치되지는 않음 |
| 이번 자료의 출처 | 수업 코드의 인용이 아닌 새 추가 학습 예제 |

태그를 많이 넣는 것이 목표가 아니다. ‘이 묶음이 무엇을 하는가’를 설명할 수 있을 때 그 역할에 맞는 요소를 선택한다.

## 2. 개념부터 이해하기

### 2.1 시맨틱은 내용의 역할을 드러낸다는 뜻

같은 제목·문단이라도 페이지 소개인지 중심 내용인지 관련 안내인지 구분할 수 있다. 이 구분을 읽기 쉬운 구조로 표시하는 것이 목적이다. 화면의 위·아래·왼쪽·오른쪽 좌표만으로 요소를 선택하지 않는다.

<a id="extra-01-2"></a>

| 요소 | 선택할 때 묻는 질문 | 주의 |
| --- | --- | --- |
| header | 페이지나 구역을 소개하는가? | 반드시 화면 맨 위에만 쓰는 것은 아님 |
| nav | 주요 탐색 링크인가? | 모든 링크 묶음에 무조건 붙이지 않음 |
| main | 문서의 중심 내용인가? | 새 예제는 보이는 main 하나로 명확히 구성 |
| section | 하나의 주제인가? | 그 주제를 드러내는 제목과 함께 생각 |
| article | 독립적으로 읽을 글·항목인가? | 네모 카드 모양만으로 결정하지 않음 |
| aside | 주된 흐름과 구별되는 관련 정보인가? | 오른쪽에 놓였다는 이유만으로 선택하지 않음 |
| footer | 해당 페이지·구역의 마무리 정보인가? | 물리적으로 맨 아래라는 뜻만은 아님 |
| div | 특별한 의미 없는 묶음이 필요한가? | div 사용 자체가 잘못인 것은 아님 |

> 📚 **출처 · 추가 학습 근거:** 영역의 뜻은 [HTML 표준 — Sections](https://html.spec.whatwg.org/multipage/sections.html), main·div 등은 [Grouping content](https://html.spec.whatwg.org/multipage/grouping-content.html)로 확인했다. 외부 문서에서 확인한 내용이며 실제 수업 구현으로 표시하지 않는다.

## 3. 작은 예제와 결과

**설명용 새 예제 · 추가 학습 · 전체 문서.** 아래 코드는 [08_시맨틱_추가복습.html](실습/08_시맨틱_추가복습.html)과 같다.

```html
<!DOCTYPE html>
<html lang="ko">
<head>
    <meta charset="UTF-8">
    <title>학습 기록의 영역</title>
</head>
<body>
    <header>
        <h1>학습 기록</h1>
        <nav>
            <a href="#today">오늘 배운 내용</a>
            <a href="#review">복습</a>
        </nav>
    </header>
    <main>
        <section id="today">
            <h2>오늘 배운 내용</h2>
            <article>
                <h3>폼의 name과 value</h3>
                <p>보이는 글자와 전송 값을 구분했다.</p>
            </article>
        </section>
        <section id="review">
            <h2>복습</h2>
            <p>입력 상태와 제출 항목을 다시 확인한다.</p>
        </section>
    </main>
    <aside>
        <h2>관련 공부</h2>
        <p>다음에는 CSS로 배치를 정리한다.</p>
    </aside>
    <footer>
        <p>나의 공부 기록</p>
    </footer>
</body>
</html>
```

기본 표시에서는 소개·본문·관련 안내가 대체로 문서 순서대로 놓인다. aside를 썼다고 오른쪽 칸이 자동 생성되는 것은 아니다. 메뉴의 href와 section의 id가 맞으므로 이미 배운 문서 안 이동도 적용된다.

**한 가지 변경 실험:** aside의 태그만 div로 바꾸면 글자는 비슷하게 보일 수 있다. 그래도 작성한 의미는 ‘관련 보조 정보’에서 ‘일반 묶음’으로 달라진다. 이 실험은 화면 모양만으로 구조의 의미를 판단할 수 없음을 보여 준다.

<a id="my-code"></a>

## 4. 내 코드와의 관계

이번 예문은 내 수업 원본의 숨겨진 구현을 찾아낸 것이 아니다. 배운 제목·문단·링크를 바탕으로 **영역 요소를 새로 학습하는 자료**다.

| 이미 배운 부분 | 추가한 부분 |
| --- | --- |
| h1·h2·h3의 제목 단계 | 그 제목이 속할 페이지 영역 |
| p의 문단 | 중심 글·보조 글의 구분 |
| href와 id | 주요 탐색을 nav로 묶기 |

원본 코드와 비교할 기능이 없는 곳에 강사님·내 코드 발췌를 억지로 만들지 않는다. 그 대신 새 예제의 근거와 학습 범위를 분명히 표시한다.

<a id="connections"></a>

## 5. 다른 파일과 연결하기

이 예제는 한 파일에서 동작한다. 메뉴는 `#today`·`#review`로 같은 문서의 section을 찾는다. 별도 CSS나 JS 파일을 import하지 않았고 서버 함수도 없다.

```text
header: 소개와 주요 메뉴
   → main: 오늘 내용과 복습
   → aside: 관련 공부
   → footer: 마무리
```

이 그림은 읽는 역할의 흐름이다. 가로 칸을 만드는 배치 설계는 뒤의 CSS와 연결한다. 의미 있는 영역을 선택했다고 화면 레이아웃·접근성·검색 노출이 모두 자동 완성되는 것은 아니다.

## 6. 선택을 검토하기

| 선택 | 이 예제에서의 이유 | 다시 생각할 경우 |
| --- | --- | --- |
| main 하나 | 중심 내용을 분명히 묶음 | 다른 보이는 main을 중복해서 만들지 않았는지 |
| section마다 제목 | 주제별 영역을 식별 | 단순 스타일용 상자를 주제로 착각했는지 |
| article | 하나의 독립적인 학습 항목 | 단지 카드 모양이라 선택한 것은 아닌지 |
| aside | 중심 글과 구별한 관련 안내 | 배치 방향만으로 고른 것은 아닌지 |

**새 예제의 검토**이지 당시 내 코드의 장단점 평가가 아니다. 영역 요소가 적어도 목적에 충분할 수 있고, div가 있어도 그 자체로 결함은 아니다. 역할을 설명할 수 없는 요소를 수만 늘려 넣지 않는다.

<a id="teacher"></a>

## 7. 강사님 코드 비교의 범위

비교한 HTML 기초 원본에서는 이 페이지 영역 구성을 필수 구현으로 확인하지 않았다. 따라서 여기에는 강사님 코드 인용이나 ‘강사님 방식이 더 좋다’는 평가를 붙이지 않는다. 앞선 기본 장의 실제 비교는 그대로 학습 근거로 사용하고, 이 장은 선택 부록으로 읽는다.

<a id="results"></a>

## 8. 결과와 확인 방법

| 확인할 것 | 방법 |
| --- | --- |
| 페이지의 역할 | 각 영역을 한 문장으로 설명 |
| 제목 단계 | h1→h2→h3의 주제 연결 확인 |
| 메뉴 목적지 | href 식별자와 실제 id 일치 |
| 표시와 의미 | CSS 없이도 의미를 설명할 수 있는지 |

새 파일의 구조와 식별자 연결은 정적으로 확인한다. 스크린 리더·모든 브라우저의 접근성 트리를 실행 검사한 기록은 아니다. 화면에서 잘 보인다는 사실만으로 전체 접근성이 검증됐다고 쓰지 않는다.

## 9. 추가로 알면 좋은 것

> 💡 **TIP · 이 선택 부록의 추가 확장:** 보조 기술이 주요 영역을 찾아가는 단서가 되는 역할을 랜드마크라고 한다. 여러 탐색 영역을 구분해야 한다면 aria-label 같은 이름을 추가하는 방법도 공부할 수 있다. 모든 요소에 ARIA를 덧붙이는 것이 목표는 아니다. [출처: W3C WAI — Landmark Regions](https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/).

예를 들어 `nav aria-label="주요 메뉴"`는 탐색 영역의 이름을 지정한다. 기본 폼의 label·id 연결로 해결하는 문제를 무조건 ARIA로 바꾸지 않는다. 이름·역할·상태의 자세한 설계와 실제 보조 기술 검수는 별도 학습으로 남긴다.

## 10. 선택 복습과 다음 학습

1. 오른쪽에 보이는 상자는 언제나 aside일까?
2. section을 만들면 그 안의 제목은 모두 h1로 시작할까?
3. 메뉴의 목적지 하나를 새 section으로 바꾸려면 무엇을 같이 맞춰야 할까?

<details>
<summary>해설</summary>

배치보다 내용의 역할을 먼저 판단하므로 첫 답은 아니다. 제목은 문서의 주제 단계에 맞춰 선택하며 section을 썼다는 이유만으로 모두 h1로 만들지 않는다. 메뉴는 href와 도착 id를 함께 맞춘다.

</details>

| 빠른 판단 | 물을 질문 |
| --- | --- |
| 영역 | 무엇을 하는 묶음인가? |
| 제목 | 그 역할과 주제가 읽히는가? |
| 스타일 | 의미와 모양을 혼동하지 않았는가? |
| 범위 | 새 예제를 실제 수업 구현으로 표시하지 않았는가? |
