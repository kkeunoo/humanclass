# FastAPI 종합실습 — 폼 Todo의 요청 흐름 연결하기

[FastAPI 목차](README.md) · [화면 Todo 원본 비교](05_FastAPI_Jinja_Todo_CRUD.md)

**수업에서 배운 GET·POST, Jinja, 폼 값, 메모리 목록, 303 리다이렉트를 묶은 새 복습**이다. 실제 강사님 완성 과제나 내 당시 제출 코드가 아니다. 아래는 기존 경로를 바꾸는 요구가 아니라 원본 동작을 설명할 수 있는지 확인하는 순서다.

## 만들어 볼 흐름

1. `GET /create`에서 입력 폼을 보여 준다.
2. 폼의 `name="id"`, `name="item"` 값을 `POST /create`로 보낸다.
3. 서버는 값을 읽고 비어 있지 않으면 목록에 추가한다.
4. `303`으로 목록 주소에 이동하고, 새 GET 요청에서 항목을 보여 준다.
5. 항목 하나를 수정·삭제할 때 **어느 id를 고르는지** 설명한다.

내 [05장 원본](05_FastAPI_Jinja_Todo_CRUD.md)은 `request.form()`으로 값을 읽고 딕셔너리 목록에 저장한다. 강사님은 `Todo = Form()` 모델을 쓴다. 두 방식의 자료 형태를 섞지 않은 채, 하나를 선택해 종이에 각 단계의 값과 요청 방식을 적는다.

<details>
<summary>흐름 해설 — 먼저 직접 추적한 뒤 펼치기</summary>

| 요청 | 읽는 값 | 메모리 상태 | 다음 동작 |
| --- | --- | --- | --- |
| GET 입력 화면 | 없음 | 변화 없음 | 폼 템플릿 표시 |
| POST 생성 | `id`, `item` | 값이 유효하면 딕셔너리 추가 | 303 반환 |
| GET 목록 | 현재 목록 | 변화 없음 | Jinja로 항목 표시 |
| 수정·삭제 요청 | 대상 `id` | 찾은 항목 변경 또는 제거 | 목록 표시 또는 리다이렉트 |

`RedirectResponse`가 목록 HTML을 직접 렌더링하는 것이 아니다. 브라우저가 지정 주소로 다시 요청한다. 목록은 DB가 아니라 메모리에 있으므로 서버 재시작 후 유지되지 않는다.

</details>

## 성공 기준

같은 화면을 다시 열었을 때 요청 방식과 저장 위치를 설명할 수 있고, 빈 값이 들어왔을 때 내 코드의 분기가 어디로 보내는지 말할 수 있다. DB까지 넓히고 싶다면 [SQLite](06_Python_SQLite와_Transaction.md)를 읽되 이 기본 실습의 필수 조건으로 넣지 않는다.

## 추가로 알면 좋은 것

실제 서비스를 위한 인증, 동시성, 영속 저장 설계, `response_model`은 이 재구성 복습에서 요구하지 않는다. 원본에 없는 기능을 추가하면 새 실험으로 기록한다.
