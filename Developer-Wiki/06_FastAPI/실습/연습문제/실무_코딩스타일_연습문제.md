# FastAPI 실무 스타일 — 경로·처리·응답의 책임을 읽기 쉽게 나누기 — 연습문제

[본문](../../실무_코딩스타일.md) · [문제 목차](README.md)

실제 수업 내용을 바탕으로 **새로 구성한 연습문제**다. 원본·당시 내 코드·새 개선안을 구별한다. 예상 → 이유 → 한 가지 변경 순서로 푼다.

## 목표와 준비

경로 함수와 재사용할 조회·변경 함수를 나눈다. 인자·반환·None·응답 상태·리다이렉트를 연결한다. 이름·줄바꿈 정리와 논리 수정·새 정책을 구별하고, 과도한 분리를 피하는 판단 기준을 설명한다.

[본문 3절](../../실무_코딩스타일.md#example)의 폴더·설치·입력·실행 조건부터 확인한다. 아래 필요한 파일 전체를 같은 구조로 저장한다. 가져오는 함수·모델 정의도 빠뜨리지 않는다.

## 문제 1. 요청과 결과 예상

**todo_service.py**

```python
todos = [{'id': 1, 'item': '공부'}]

def find_todo(todo_id):
    for todo in todos:
        if todo['id'] == todo_id:
            return todo
    return None

def rename_todo(todo_id, item):
    todo = find_todo(todo_id)
    if todo is None:
        return False
    todo['item'] = item
    return True
```

**api.py**

```python
from fastapi import FastAPI, Form, HTTPException
from fastapi.responses import RedirectResponse
from todo_service import find_todo, rename_todo

app = FastAPI()

@app.get('/todos/{todo_id}')
def read_todo(todo_id: int):
    todo = find_todo(todo_id)
    if todo is None:
        raise HTTPException(status_code=404, detail='없는 ID')
    return todo

@app.post('/todos/update')
def update_todo(todo_id: int = Form(), item: str = Form()):
    changed = rename_todo(todo_id, item)
    if not changed:
        raise HTTPException(status_code=404, detail='없는 ID')
    return RedirectResponse(f'/todos/{todo_id}', status_code=303)
```

실행 전에 결과를 먼저 적는다. 상태·응답·서버 출력·변경된 자료를 구별한다.

<details>
<summary>풀이</summary>

| 요청 | 결과 |
| --- | --- |
|GET /todos/1 | 공부 |
|없는99번 |404 |
|정상 수정 |303→/todos/1 |
|다시 조회 | 복습 |
|잘못된 숫자 |422 |

조회 경로는 정수ID를 find_todo에 넘긴다. 도우미가 찾은 dict는 원래 목록의 항목과 같은 객체다. 수정 도우미가 item을 바꾸면 다음 조회에서 복습을 읽는다. 없는 ID는 도우미가 None또는False로 알려 주고 경로 함수가404를 만든다. 정상 수정은303뒤 조회로 이어진다. 잘못된 숫자는 프레임워크 입력 단계에서422가 된다.

| 실패 위치 | 값·상태 | 누가 결정 |
| --- | --- | --- |
|입력 숫자 변환 |422 | 프레임워크 |
|조회 없음 | None | 도우미 |
|HTTP없는 대상 |404 | 경로 함수 |
|정상 수정 |True·303 | 도우미·경로 함수 |

</details>

## 문제 2. 이유 설명

1. None과404를 같은 함수가 반드시 만들어야 하는가?
2. print만 하면 호출자가 dict를 받는가?
3. 함수 이름 정리와404정책 추가는 같은 변경인가?
4. 파일을 많이 나누면 언제나 더 좋은가?

<details>
<summary>풀이</summary>

도우미의 자료 계약과 HTTP응답 정책을 나눌 수 있다. 반환해야 받는다. 표현과 동작 변경을 구별한다. 의미 있는 책임과 읽기 흐름을 기준으로 판단한다.

</details>

## 문제 3. 한 가지만 바꾸기

| 한 가지만 변경 | 예상 | 이유 |
| --- | --- | --- |
|도우미의 정상 return제거 | 호출자가성공값못받음 | 반환 계약 변경 |
|파일만옮기고import유지 | 모듈탐색실패가능 | 경로 연결 |
|함수이름만일관되게변경 | 결과동일 | 표현 정리 |
|404를안내dict로변경 | 상태정책변경 | 단순 스타일 아님 |

<details>
<summary>막힐 때 확인</summary>

None을 dict처럼 읽는 오류면 반환 경로를 확인한다. 모듈 이름만 바꾸지 말고 실제 import와 호출도 함께 확인한다. 로직을 분리한 뒤 값이 달라지면 객체를 복사했는지 원래 객체를 수정했는지 본다. DB앱에서는 파일 분리 전에 자원과 트랜잭션 소유자를 먼저 정한다.

</details>

## 채점과 복습

정상 값만 보지 말고 누락·잘못된 타입·없는 대상의 흐름도 설명한다. 새 예제는 별도 앱에서 확인하며 원본 DB나 외부 서비스의 성공을 대신 주장하지 않는다. TIP 확장은 필수 조건이 아니다. 정의→등록→입력→호출→반환→다음 요청을 연결할 수 있는지 검토한다.
