# FastAPI 실무 스타일 — 경로·처리·응답의 책임을 읽기 쉽게 나누기

[FastAPI 목차](README.md) · [읽기 안내](00_FastAPI_상세백과_읽기법.md)

실무 스타일은 긴 함수를 무조건 여러 파일로 나누는 규칙이 아니다. 요청에서 온 값, 저장소에서 찾은 값, 사용자가 보는 응답을 구분해 다음 사람이 흐름을 이해할 수 있게 만드는 일이다. 이 장은 실제 수업을 재구성한 새 연습이다.

## 1. 이 장에서 배울 것

경로 함수와 재사용할 조회·변경 함수를 나눈다. 인자·반환·None·응답 상태·리다이렉트를 연결한다. 이름·줄바꿈 정리와 논리 수정·새 정책을 구별하고, 과도한 분리를 피하는 판단 기준을 설명한다.

<a id="concepts"></a>

## 2. 무엇이며, 왜 필요한가

경로 함수는 HTTP입력과 응답을 연결하는 역할을 맡는다. 조회 도우미는 주어진 ID로 항목을 찾고 결과를 돌려준다. 이 둘을 나누면 브라우저 요청 없이도 조회 함수의 의미를 설명할 수 있다. 단, 두 줄마다 함수를 만들면 오히려 여러 정의를 오가야 하므로 목적이 분명한 단위부터 나눈다.

| 경계 | 입력 | 반환·효과 |
| --- | --- | --- |
| find_todo | 정수ID | dict 또는 None |
| rename_todo | 정수ID·새 내용 | 변경 성공 여부 |
| 경로 조회 | 경로값·Request문맥 | JSON 또는404 |
| 경로 수정 | 폼값 | 성공 뒤303 또는404 |

find_todo가 None을 반환하는 것은 도우미의 계약이다. HTTP404로 응답할지는 경로 함수가 정한다. 함수 내부에서 print했다고 호출자에게 자료를 준 것은 아니므로 반환값을 명시해야 한다. 실제 DB앱에서는 Session수명과 commit/rollback경계도 같은 방식으로 누가 맡는지 정해야 한다.

> 📚 **출처 · 본문 설명 확인:** [FastAPI 여러 파일 앱](https://fastapi.tiangolo.com/tutorial/bigger-applications/), [오류 처리](https://fastapi.tiangolo.com/tutorial/handling-errors/). 배운 의미 확인 근거다. 아래 표·전체 예제·풀이를 외부 문장 그대로 옮기지 않았다. 확인일: 2026-10-30.

## 3. 작은 예제로 먼저 이해하기

**새 설명 예제 · 필요한 파일 전체.** 같은 장의 폴더 구조를 유지한다. api.py와 todo_service.py를 같은 폴더에 둔다. FastAPI·Uvicorn·python-multipart가 필요하다. api.py폴더에서 `uvicorn api:app --port 8000 --reload`로 실행한다. 초기 자료는 ID1·내용공부 한 개다. 새 예제는 메모리 저장이며, DB연결·인증을 추가한 코드가 아니다.



**[todo_service.py](실습/책형_복습/실무_코딩스타일/todo_service.py) — 새 예제 전체 파일**

```python
todos = [{'id': 1, 'item': '공부'}]

def find_todo(todo_id):
    for todo in todos:
        if todo['id'] == todo_id:
            return todo
    return None

def rename_todo(todo_id, item):
    todo = find_todo(todo_id)
    if todo is None:
        return False
    todo['item'] = item
    return True
```

**[api.py](실습/책형_복습/실무_코딩스타일/api.py) — 새 예제 전체 파일**

```python
from fastapi import FastAPI, Form, HTTPException
from fastapi.responses import RedirectResponse
from todo_service import find_todo, rename_todo

app = FastAPI()

@app.get('/todos/{todo_id}')
def read_todo(todo_id: int):
    todo = find_todo(todo_id)
    if todo is None:
        raise HTTPException(status_code=404, detail='없는 ID')
    return todo

@app.post('/todos/update')
def update_todo(todo_id: int = Form(), item: str = Form()):
    changed = rename_todo(todo_id, item)
    if not changed:
        raise HTTPException(status_code=404, detail='없는 ID')
    return RedirectResponse(f'/todos/{todo_id}', status_code=303)
```

조회 경로는 정수ID를 find_todo에 넘긴다. 도우미가 찾은 dict는 원래 목록의 항목과 같은 객체다. 수정 도우미가 item을 바꾸면 다음 조회에서 복습을 읽는다. 없는 ID는 도우미가 None또는False로 알려 주고 경로 함수가404를 만든다. 정상 수정은303뒤 조회로 이어진다. 잘못된 숫자는 프레임워크 입력 단계에서422가 된다.

**요청과 예상 결과:**

| 요청 | 결과 |
| --- | --- |
|GET /todos/1 | 공부 |
|없는99번 |404 |
|정상 수정 |303→/todos/1 |
|다시 조회 | 복습 |
|잘못된 숫자 |422 |

## 5. import·함수·화면·저장이 연결되는 흐름

api.py의 import → todo_service.py의 목록·두 함수 정의 → 경로ID또는폼값 → 조회·변경 도우미 → 반환 결과 → HTTP예외 또는303 → 다음GET이다. 도우미가 HTTP를 몰라도 되고 경로 함수가 모든 반복문을 가질 필요도 없다. 각 파일이 맡은 책임을 먼저 적으면 나중에 저장소를 바꿀 때 연결점을 찾기 쉽다.

## 6. 잘한 점·아쉬운 점·개선 방향

**잘한 점:** 원본에서도 create·read·update·delete를 함수로 나누고 화면 이동을 명시했다. **보완:** 자료를 찾는 코드와 응답을 만드는 코드를 목적에 맞게 분리했다. **동작 변경:** 없는ID에404를 주는 것은 단순 이름 정리가 아니라 새 응답 정책이다. **한계:** 빈 내용·동시 수정·중복ID정책은 이 작은 예제에서 다루지 않는다. 추상 계층을 많이 만드는 것 자체가 실무 품질은 아니다.

원본 오류·수업용 단순화·목적에 따른 설계를 나눈다. 새 개선안은 당시 내 코드나 D 드라이브 수정본이 아니다.

## 7. 강사님 코드가 도움이 되는 비교



강사님 상세의 현재 목록 조회와303이동은 참고할 만한 흐름이다. 강사님 전체 구현을 복사하기보다 학생 저장 형식·학습 문법에 맞춰 새 도우미를 구성했다. 원본과 달라진 반환·정책을 함께 적어 공정하게 비교한다.

## 8. 결과를 추적하고 한 가지 바꾸기

| 실패 위치 | 값·상태 | 누가 결정 |
| --- | --- | --- |
|입력 숫자 변환 |422 | 프레임워크 |
|조회 없음 | None | 도우미 |
|HTTP없는 대상 |404 | 경로 함수 |
|정상 수정 |True·303 | 도우미·경로 함수 |

| 한 가지만 변경 | 예상 | 이유 |
| --- | --- | --- |
|도우미의 정상 return제거 | 호출자가성공값못받음 | 반환 계약 변경 |
|파일만옮기고import유지 | 모듈탐색실패가능 | 경로 연결 |
|함수이름만일관되게변경 | 결과동일 | 표현 정리 |
|404를안내dict로변경 | 상태정책변경 | 단순 스타일 아님 |

None을 dict처럼 읽는 오류면 반환 경로를 확인한다. 모듈 이름만 바꾸지 말고 실제 import와 호출도 함께 확인한다. 로직을 분리한 뒤 값이 달라지면 객체를 복사했는지 원래 객체를 수정했는지 본다. DB앱에서는 파일 분리 전에 자원과 트랜잭션 소유자를 먼저 정한다.

**확인 범위:** 새 앱을 별도 임시 폴더에 복사해 프레임워크 요청·응답 흐름으로 확인한다. 실제 외부 서비스·운영 DB·브라우저 공개 서버에 요청한 결과와 구별한다. 원본 전체 앱을 무조건 실행하지 않으며 별도 확인한 원본 구간은 검증 보고서에 기록한다. 사용자의 가상환경은 검사에 읽기만 사용하고 파일을 설치·수정하지 않는다.

## 9. 추가로 알면 좋은 것과 출처

> 💡 **TIP · 수업 범위 밖:** 서비스·저장소 계층의 상세 설계, 타입 검사 도구, 테스트용 의존성 교체, 로그·설정 관리·정교한 오류 모델은 추가 학습이다. 현재는 실제 배운 함수·import·폼·반환·HTTPException으로 경계를 설명한다.

request.headers 직접 읽기와 response_model은 미학습으로 확인된 선택 확장이다. 본문에서 이 기능을 선행 조건으로 요구하지 않는다. 응답·입력 타입 표시와 response_model 설정도 구별한다.
