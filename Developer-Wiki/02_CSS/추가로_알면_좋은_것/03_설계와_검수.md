## 1. 이름과 파일을 정하는 이유

```css
/* 추가 설계 예시. 수업 원본 이름을 바꾼 코드가 아님 */
.course-card { padding: 20px; }
.course-card__title { font-size: 24px; }
.course-card--featured { border: 2px solid blue; }
```

BEM 형태의 이름은 블록·안쪽 요소·변형의 관계를 알아보기 위한 약속이다. 이 이름만 붙이면 특별한 CSS 기능이 생기지는 않는다. 단순한 수업 상자에 반드시 적용할 의무도 없다.

| 설계 선택 | 판단할 질문 |
| --- | --- |
| 공통 클래스·유틸리티 | 실제로 같은 역할·같은 변경 이유를 공유하는가 |
| 상태 클래스 | 상태를 누가 언제 바꾸는가. CSS만으로 업무 상태가 저장되는가 |
| 파일 분리 | 반복되는 규칙과 적용 순서를 찾기 쉬운가 |
| 디자인 토큰 | 이름을 바꾸면 어떤 화면이 함께 바뀌는가 |
| cascade layer | 명시도 경쟁과 별개로 선언 묶음의 우선순위를 설계할 필요가 있는가 |

레이어까지 사용하면 기본편의 단순 우선순위 예제보다 조건이 늘어난다. 레이어를 적용했다고 !important가 불필요해지는 등 단정적인 결론을 만들지 않는다. [캐스케이드 표준](https://www.w3.org/TR/css-cascade-5/#layering)

## 2. 화면 검수는 한 종류의 검사가 아니다

| 확인할 것 | 관찰할 증거 |
| --- | --- |
| 문법·선택자 | 선언 유효성, 실제로 매칭된 요소 |
| 크기·간격 | 계산된 값과 화면의 테두리 경계 |
| 반응형 | 조건 경계 바로 아래·경계값·바로 위 |
| 상호작용 | 포인터 진입·이탈, Tab 이동, 버튼 활성화 |
| 외부 자원 | 이미지·글꼴 요청 성공과 실제 표시 |
| 접근성 | 의미·이름·키보드·보조 기술을 함께 검토 |
| 성능 | 실제 측정과 반복 재현. 속성 이름만 보고 빠르다고 단정하지 않음 |

문법 검사 통과가 폼 전송·접근성·모든 브라우저 동작까지 보장하지 않는다. 검증을 위해 쓴 JavaScript 진단 도구도 CSS 수업의 필수 진도에 넣지 않는다. 이번 작업의 검사 범위는 [최종 기록](../../편집기록/02_CSS_최종_검증기록.md)에 구분했다.

## 3. 큰 프로젝트를 단계로 나누기

먼저 기본 display 실습을 설명한다. 그다음 배치를 Grid로 바꾸고, 포커스 표시를 추가하고, 필요한 경우 색상 체계와 반응형 조건을 확장한다. 여러 새 기능을 한 번에 넣고 무엇 때문에 결과가 바뀌었는지 모르는 상태를 피한다.

[추가 프로젝트](04_학습카드_확장프로젝트.md)는 이 과정을 위한 작은 출발점이다. 기존 대시보드의 사이드바·진행률·알림·다크 모드 전체를 기본 복습의 성공 조건으로 요구하지 않는다.
