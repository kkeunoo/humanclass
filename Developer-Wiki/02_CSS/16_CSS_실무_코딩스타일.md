# 16. CSS 작성 스타일 — 의도·연결·계산을 읽기 쉽게

[CSS 목차](README.md) · [읽기 안내](00_CSS_V3_동작_백과_읽기법.md)

다시 읽기 좋은 CSS는 새 속성을 많이 쓰는 코드보다 적용 대상과 변경 이유를 찾기 쉬운 코드다. 문법 오류와 관찰용 실험, 선택 가능한 스타일을 나눠 고치는 습관을 배운 코드에 적용한다.

## 1. 이 장에서 배울 것

실제 오타가 어떤 선언을 무효로 만드는지 설명한다. 이름·적용 순서·크기·상태를 검토하고, 확인용 색 변경과 오류 교정을 구분한다.

이번 장의 개념과 원본 기능은 수업 범위다. 원본에 없는 선택 기능은 9절 TIP으로 구분한다. 결과를 읽을 때는 선택된 요소·속성·기준값·실행 상태를 함께 적는다.

<a id="concepts"></a>

## 2. 무엇이며, 왜 필요한가

CSS를 고칠 때는 ‘파일이 연결되었는가 → 선택자가 맞는가 → 선언이 유효한가 → 다른 선언이 이겼는가 → 계산 기준이 맞는가’ 순서로 좁혀 간다. 테두리가 안 보인다고 무조건 더 큰 숫자나 !important를 붙이는 것은 원인을 설명하지 못한다.

| 종류 | 실제 사례 | 판단 |
| --- | --- | --- |
| 문법·값 오류 | border의 sold | solid로 교정 필요 |
| 구조 오류 | p 안의 div | HTML부터 교정 |
| 수업용 실험 | 같은 속성의 연속 선언·주석 후보 | 현재 활성값을 표시 |
| 설계 선택 | 공통 클래스와 태그 한정 클래스 | 적용 범위·목적 기준 |
| 표현 선택 | 들여쓰기 2칸·4칸 | 팀 안의 일관성 기준 |

같은 규칙 안에 잘못된 선언이 있어도 모든 유효한 선언이 함께 사라지는 것은 아니다. border 값 하나가 무효인 경우 padding·font-size는 별도로 적용될 수 있다. 화면이 비슷해 보이는 것과 문법이 유효한 것도 같은 판단은 아니다.

> 📚 **출처 · 본문 설명 확인:** [W3C 캐스케이드와 값 처리](https://www.w3.org/TR/css-cascade-5/) 및 [박스·테두리](https://www.w3.org/TR/CSS2/box.html#border-properties). 설명과 비교 표는 수업 원본을 바탕으로 새로 풀어 썼다. 외부 원문을 직접 인용한 문장은 아니다. 확인일: 2026-10-28.

<a id="example"></a>

## 3. 작은 예제로 먼저 이해하기

**새 설명 예제 · 전체 파일.** [실행 파일](실습/책형_복습/16_CSS_실무_코딩스타일.html)을 브라우저로 연다. 이 예제는 위 style 안에 CSS를 모두 넣어 외부 파일 연결이 필요 없다. 원본 CSS에 붙이면 다른 규칙이 섞일 수 있으므로 먼저 별도 파일로 확인한다.

```html
<!DOCTYPE html>
<html lang="ko">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>16. CSS 작성 스타일 — 의도·연결·계산을 읽기 쉽게</title>
    <style>
        .msg { background-color: white; font-size: 15px; border: 1px solid #555555; padding: 5px; border-radius: 10px; }
        .msg:hover { background-color: lightblue; }
    </style>
</head>
<body>
    <h1>의도를 남기는 작성</h1>
    <div class="msg">테두리와 안쪽 간격을 관찰합니다.</div>
</body>
</html>
```

이 새 개선 예제는 실제 오타 sold를 solid로 고치고, 흰 배경에서 확인하기 쉽도록 테두리 색도 진한 회색으로 바꿨다. **오타 교정**과 **관찰용 색 선택**은 서로 다른 수정이다. 간격은 padding5px, 테두리는1px이며 모서리10px가 너비 계산을 없애지는 않는다.

## 4. 내가 작성한 코드를 따라 읽기

아래는 **내 원본 발췌**다. 주석의 표현도 원문대로 두었다. 설명에서 교정한 내용을 원본에 이미 수정한 것처럼 읽지 않는다.

### 내 코드 — 원본 발췌

출처: `D:/workspace/workspace_html/css/실습_개인/asset/css/연습_01.css` 11–20행

```css
div.msg {
    background-color: #ffffff;

    font-size: 15px;
    border: 1px sold #ffffff;

    padding: 5px;

    border-radius: 10px;
}
```

**발췌 바로 풀이:** `sold`는 올바른 border-style 값이 아니다. 그 border 선언이 무효가 되며, 같은 규칙의 font-size·padding까지 모두 무효가 되는 것은 아니다.

아래는 내 개인 실습 파일이다. 같은 위치의 강사님 과제가 없으므로 양쪽 동일 과제라고 쓰지 않는다. border의 sold는 올바른 스타일 값이 아니어서 그 선언이 무효다. font-size15px·padding5px·radius10px는 각자 별도 선언이다. 원본은 흰 배경·흰 테두리여서 오타만 고쳐도 화면 차이가 잘 안 보일 수 있다.

<a id="connections"></a>

## 5. 파일·요소·값이 연결되는 흐름

HTML의 class="msg" → 원본 div.msg 조건 → 유효한 선언과 무효 선언 구분 → 우선순위·계산값 → 화면 확인 순서다. .msg로 바꾸면 div 외 다른 태그도 같은 클래스로 적용받을 수 있다. p.msg로 좁히면 현재 div에는 맞지 않는다. 이름을 바꾼 뒤 참조도 함께 보아야 한다.

<a id="review"></a>

## 6. 잘한 점·아쉬운 점·개선 방향

**잘한 점:** 개인 실습에 수업의 border·여백·글꼴을 연결했다. **실제 오류:** sold는 교정한다. **선택:** div.msg와 .msg 중 어느 쪽이 좋은지는 사용할 범위에 달려 있다. **개선 방향:** 같은 속성의 최종값을 찾기 쉽게 정리하되 대체값이나 단계적 지원을 위한 앞 선언까지 무조건 삭제하지 않는다. 주석은 코드가 무엇인지 반복하기보다 왜 그 조건인지 설명하면 유익하다.

제안은 원본을 수정한 결과가 아니다. **실제 오류**, **관찰을 위한 수업용 단순화**, **목적에 따라 가능한 선택**을 구별한다. 단지 짧게 쓰거나 최신 기능을 쓴다고 더 좋은 코드는 아니다.

<a id="teacher"></a>

## 7. 강사님 코드가 도움이 되는 비교



이 개인 파일은 같은 강사님 원본이 없어 비교를 만들지 않는다. 앞 장의 비교에서 가져올 판단은 양쪽도 같은 오류를 가질 수 있고, 내 코드가 설명하기 좋은 구조를 가질 수도 있다는 점이다. 권위보다 동작과 요구사항으로 검토한다.

<a id="results"></a>

## 8. 결과를 예상하고 한 가지 바꾸기

아래는 **명시한 조건에서의 코드 기준 예상**이다. 이번 편집에서 실제 브라우저 렌더링을 재실행했다는 기록과 구별한다. 매 실험은 원래 예제로 돌아가 한 조건만 바꾼다.

| 한 가지 변경 | 예상 | 검토 |
| --- | --- | --- |
| solid만 sold로 | 해당 border 선언 무효 | 나머지 선언 별도 |
| 원래 색만 white로 | 경계 구별 어려울 수 있음 | 문법 오류는 아님 |
| 원래 .msg만 p.msg로 | 현재 div에 미적용 | 대상 범위 변경 |
| 원래 padding만10px | 안쪽 간격 증가 | 박스 계산 재확인 |

빠르게 찾을 곳은 [선택자](01_CSS_선택자와_적용방법.md), [우선순위](01-02_CSS_우선순위와_상속.md), [박스](03_CSS_박스모델.md), [위치](08_CSS_Position과_요소위치.md), [전환](12_CSS_Transition과_상태변화.md)이다. 구조 검사·실제 화면·반응형 경계·상호작용은 별도 증거로 기록한다. 한 종류의 검사 통과가 모든 동작을 보장하지 않는다.

## 9. 추가로 알면 좋은 것과 출처

> 💡 **TIP · 수업 범위 밖:** BEM·레이어·디자인 토큰 전체 체계·새 선택자·성능 최적화 도구는 추가 학습이다. 원본 var·font-display의 기본 사용까지 미학습으로 보내지는 않는다.

> [!TIP]
> 이하의 설계·검수 도구와 이름 규칙은 **수업 원본에서 확인된 필수 진도가 아닌 추가 학습**이다. 위의 선택자·선언·오타 교정을 먼저 설명할 수 있으면 이 장의 기본 목표를 달성한 것이다.

<a id="extra-03-1"></a>

### 1. 이름과 파일을 정하는 이유

```css
/* 추가 설계 예시. 수업 원본 이름을 바꾼 코드가 아님 */
.course-card { padding: 20px; }
.course-card__title { font-size: 24px; }
.course-card--featured { border: 2px solid blue; }
```

BEM 형태의 이름은 블록·안쪽 요소·변형의 관계를 알아보기 위한 약속이다. 이 이름만 붙이면 특별한 CSS 기능이 생기지는 않는다. 단순한 수업 상자에 반드시 적용할 의무도 없다.

| 설계 선택 | 판단할 질문 |
| --- | --- |
| 공통 클래스·유틸리티 | 실제로 같은 역할·같은 변경 이유를 공유하는가 |
| 상태 클래스 | 상태를 누가 언제 바꾸는가. CSS만으로 업무 상태가 저장되는가 |
| 파일 분리 | 반복되는 규칙과 적용 순서를 찾기 쉬운가 |
| 디자인 토큰 | 이름을 바꾸면 어떤 화면이 함께 바뀌는가 |
| cascade layer | 명시도 경쟁과 별개로 선언 묶음의 우선순위를 설계할 필요가 있는가 |

레이어까지 사용하면 기본편의 단순 우선순위 예제보다 조건이 늘어난다. 레이어를 적용했다고 !important가 불필요해지는 등 단정적인 결론을 만들지 않는다. [캐스케이드 표준](https://www.w3.org/TR/css-cascade-5/#layering)

<a id="extra-03-2"></a>

### 2. 화면 검수는 한 종류의 검사가 아니다

| 확인할 것 | 관찰할 증거 |
| --- | --- |
| 문법·선택자 | 선언 유효성, 실제로 매칭된 요소 |
| 크기·간격 | 계산된 값과 화면의 테두리 경계 |
| 반응형 | 조건 경계 바로 아래·경계값·바로 위 |
| 상호작용 | 포인터 진입·이탈, Tab 이동, 버튼 활성화 |
| 외부 자원 | 이미지·글꼴 요청 성공과 실제 표시 |
| 접근성 | 의미·이름·키보드·보조 기술을 함께 검토 |
| 성능 | 실제 측정과 반복 재현. 속성 이름만 보고 빠르다고 단정하지 않음 |

문법 검사 통과가 폼 전송·접근성·모든 브라우저 동작까지 보장하지 않는다. 검증을 위해 쓴 JavaScript 진단 도구도 CSS 수업의 필수 진도에 넣지 않는다. 이번 작업의 검사 범위는 [최종 기록](../편집기록/02_CSS_최종_검증기록.md)에 구분했다.

<a id="extra-03-3"></a>

### 3. 큰 프로젝트를 단계로 나누기

먼저 기본 display 실습을 설명한다. 그다음 배치를 Grid로 바꾸고, 포커스 표시를 추가하고, 필요한 경우 색상 체계와 반응형 조건을 확장한다. 여러 새 기능을 한 번에 넣고 무엇 때문에 결과가 바뀌었는지 모르는 상태를 피한다.

[추가 프로젝트](17_CSS_종합실습.md#extra-04-1)는 이 과정을 위한 작은 출발점이다. 기존 대시보드의 사이드바·진행률·알림·다크 모드 전체를 기본 복습의 성공 조건으로 요구하지 않는다.

이 절의 확장은 기본 문제의 필수 조건이 아니다. 2절의 📚 출처는 배운 기능의 설명을 확인하는 근거이며, 출처가 있다는 이유로 모두 수업 밖 내용인 것은 아니다.

## 10. 복습과 빠른 정리

1. sold 하나 때문에 padding도 반드시 무효가 되는가?
2. 색 변경과 문법 교정은 같은 수정인가?
3. 개인 코드에 강사님과 동일 비교라고 적어도 되는가?

<details>
<summary>짧은 풀이 — 먼저 답한 뒤 확인</summary>

각 선언은 별도로 판단하므로 padding까지 반드시 무효가 되는 것은 아니다. 색은 관찰 목적의 선택이고 sold→solid는 오류 교정이다. 같은 과제 근거가 없으면 동일 비교를 만들지 않는다.

</details>
