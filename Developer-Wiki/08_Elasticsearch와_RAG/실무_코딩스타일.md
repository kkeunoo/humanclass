# Elasticsearch·RAG 실무 코딩스타일 — 구현 단계와 확인하지 않은 결과 구분하기

[단원 목차](README.md) · [종합실습](종합실습.md)

강사님과 내 `07_elastic` 코드에서 확인한 **적재 → 검색 → 청크 → 임베딩 → 질문응답** 흐름을 읽기 위한 새 점검 자료다. 원본 소스를 실제 서비스에 재실행한 기록이 아니다. `.env`·접속키는 설명에 넣지 않는다.

## 1. 저장한 필드와 검색 방식을 짝짓기

[01장](01_연결과_문서적재.md)의 매핑에서 `text`와 `dense_vector`의 목적이 다르다. [02장](02_검색과_CRUD.md)의 검색은 저장한 문서를 읽거나 바꾸는 요청이고, [04장](04_벡터와_하이브리드검색.md)의 벡터 검색은 임베딩을 이용한다. 원본 주석이 둘을 섞어 설명한 곳은 **실제 요청 필드와 함수**를 기준으로 바로잡는다.

| 읽을 위치 | 확인할 것 |
| --- | --- |
| 매핑 | 텍스트와 벡터 필드가 각각 어떤 자료를 받는가? |
| 적재 | 어떤 문서 id와 내용을 저장하는가? |
| 검색 | 단어 일치인지 벡터 유사도인지? |
| 질문응답 | 검색 결과의 어떤 내용을 질문과 함께 넘기는가? |

## 2. 청크 길이의 단위를 적기

[03장](03_청크와_임베딩.md)의 `chunk_size=30`, `overlap_size=6`은 **문자 길이** 기준이다. 앞 청크의 끝 6글자를 다음 청크 앞에 붙인다. 한 문장이 30글자를 넘으면 이 구현만으로 반드시 더 잘게 잘리는 것은 아니다. “30 토큰” 또는 “항상 최대 30자”로 바꿔 적지 않는다.

## 3. 검증 범위를 결과와 함께 쓰기

원본 `run.py`는 파일 끝에서 적재를 호출하므로, 이 Wiki의 문서 검증을 위해 실행하지 않았다. 외부 Elasticsearch와 AI 서비스의 응답·순위·답변 품질도 재현하지 않았다. 코드의 **요청 구조와 데이터 이동**은 설명할 수 있지만, 화면에 나타날 구체적인 검색 결과를 성공 사례로 적지 않는다.

## 추가로 알면 좋은 것

검색 품질 지표, 운영 권한·재시도·비용 관리, 다른 RAG 프레임워크는 이 수업 코드의 중심이 아니다. 새 학습을 덧붙이면 본문 원본과 분리한다.
