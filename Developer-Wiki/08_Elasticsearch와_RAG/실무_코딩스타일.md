## 1. 이 장에서 배울 것

파일 읽기·변환·요청·응답 가공의 책임을 나눈다. 필수 ID와 중복 ID, 같은 객체 참조를 점검하고 예외·빈 목록·성공 결과를 구별한다. 당시 코드와 새 개선안의 경계를 유지한다.

## 2. 무엇이며, 왜 필요한가

### 실행하지 않고 확인할 수 있는 부분을 먼저 분리한다

원본 ingest 함수 안에는 파일 읽기, 반복 변환, 외부 임베딩, 작업 쌓기, 실제 적재가 함께 있다. 입력이 잘못됐다는 사실을 마지막 전송 중에 알면 이미 일부 자료가 변경됐을 수 있다. 먼저 JSON과 ID·본문을 확인하고 작업을 구성한 뒤 전송 경계를 따로 두면 어느 단계에서 문제가 났는지 설명하기 쉽다.

| 경계 | 확인할 계약 | 잘못 섞었을 때 |
| --- | --- | --- |
| 읽기 | 문서 목록을 반환하거나 오류를 드러냄 | 실패가 빈 자료처럼 보임 |
| 변환 | 원본을 보존하고 독립 작업 생성 | 이전 청크가 나중 값으로 바뀜 |
| 요청 | 어느 인덱스·ID를 바꿀지 명확 | 누락 -1에 반복 덮어쓰기 |
| 응답 | 총수·현재 반환·오류 구별 | 숫자 한 개를 전체 성공으로 오해 |
| 답변 | 검색 자료와 생성 결과 추적 | 이름만 보고 서비스 판단 |

어떤 오류를 여기서 처리하고 어떤 오류를 호출자에게 알릴지도 정해야 한다. `except Exception: print(...)` 뒤 빈 dict를 반환하면 호출자는 결과 없음과 실패를 구분하기 어렵다. 작은 교재 예제에서는 잘못된 입력에 ValueError를 내도록 해 그 차이를 드러냈다. 모든 오류를 같은 HTTP 정책으로 바꾸는 설계는 별도 확장이다.

이름도 계약이다. ask_gemini가 다른 서비스를 부르거나 results를 만들고 response를 돌려주면 이름이 설명을 방해한다. 서비스와 무관한 역할 이름 또는 실제 호출에 맞는 이름을 선택하고 반환 구조를 문서화하면 이후 구현을 바꿔도 흐름을 읽기 쉽다.

> 📚 **출처 · 본문 설명 확인:** [Elastic bulk helpers](https://www.elastic.co/docs/reference/elasticsearch/clients/python/client-helpers). 함수 경계·이름·입력 검사 표는 현재 원본을 검토하여 새로 제안한 작성 방식이다. 배운 의미 확인 근거다. 아래 표·전체 예제·풀이를 외부 문장 그대로 옮기지 않았다. 확인일: 2026-10-30.

## 3. 작은 예제로 먼저 이해하기

**새 설명 예제 · 필요한 파일 전체.** 같은 장의 폴더 구조를 유지한다. Python만 필요하다. 두 파일을 같은 폴더에 저장하고 `python example.py`를 실행한다. 전송 전 작업 계획을 만드는 새 개선 예제이며 실제 Elasticsearch 클라이언트는 사용하지 않는다.



**[plan_tools.py](실습/책형_복습/실무_코딩스타일/plan_tools.py) — 새 예제 전체 파일**

```python
def plan_actions(documents):
    actions = []
    seen_ids = set()
    for doc in documents:
        doc_id = doc.get('id')
        if doc_id is None:
            raise ValueError('문서 id가 필요합니다.')
        if doc_id in seen_ids:
            raise ValueError('중복 id를 확인하세요.')
        seen_ids.add(doc_id)
        source = {**doc}
        actions.append({'_index': 'computer', '_id': doc_id, '_source': source})
    return actions
```

**[example.py](실습/책형_복습/실무_코딩스타일/example.py) — 새 예제 전체 파일**

```python
from plan_tools import plan_actions

documents = [{'id': 1, 'title': '안내'}]
actions = plan_actions(documents)
print('작업:', actions[0]['_index'], actions[0]['_id'])
print('본문 독립:', actions[0]['_source'] is not documents[0])
for invalid in [[{'title': '누락'}], [{'id': 1}, {'id': 1}]]:
    try:
        plan_actions(invalid)
    except ValueError as error:
        print(error)
print('빈 목록:', plan_actions([]))
```

plan_actions는 문서 목록을 받아 작업 목록을 돌려주고 전송하지 않는다. set은 이미 본 ID를 기억한다. source를 새 바깥 dict로 만들었지만 중첩 객체까지 깊게 복사한 것은 아니다. 현재 예제의 제목처럼 단순 값과 이후 필드 대체를 읽는 데 필요한 수준이다. ID 타입·빈 문자열·문서 필드 전체 스키마까지 검증한 함수는 아니라는 한계도 남긴다.

**실행 결과:**

```text
작업: computer 1
본문 독립: True
문서 id가 필요합니다.
중복 id를 확인하세요.
빈 목록: []
```

## 4. 내가 작성한 코드를 따라 읽기

### 내 코드 — 원본

출처: `D:/workspace/workspace_python/07_elastic/router/es_router.py` 68–89행 · **원본 발췌**

```python
def ingest_documents():
    documents = load_documents()

    actions = []

    for doc in documents :
        actions.append({
            '_index' : 'computer',
            '_id' : doc['id'], # '_id' : doc.get('id', None),
            '_source' : doc
        })

    success, errors = helpers.bulk(es, actions, stats_only=False) # stats_only=False 를 쓰면 성공/실패 값과 에러메시지를 돌려줌
    print('success : ', success)
    print('errors : ', len(errors), errors)

    return {
        'msg' : {
            'success' : success,
            'errors' : errors
        }
    }
```

**발췌 바로 풀이:** 이 함수는 파일 읽기·작업 구성·외부 적재를 한 흐름에서 한다. 전송 전 문서 목록과 ID를 확인하는 단계를 나누면 실제 변경 지점을 쉽게 검토할 수 있다.

    actions = []

## 5. import·함수·입력·출력이 연결되는 흐름

`문서 목록 → plan_actions의 ID 검사 → 새 source dict → 전송할 actions 반환 → 별도의 실제 적재 단계`다. 이번 파일은 마지막 적재 단계를 수행하지 않는다. example.py가 import한 plan_actions 정의를 plan_tools.py에 모두 제공했다. 검증 실패는 ValueError로 전달되어 바깥 try/except가 표시한다. 빈 목록은 정상 반환 []이므로 실패와 구분된다.

## 6. 잘한 점·아쉬운 점·개선 방향

**잘한 점:** 원본의 util 재사용과 명시한 인덱스·ID를 살린다. **아쉬운 점:** 넓은 예외·공유 참조·혼동되는 이름은 결과를 해석하기 어렵게 만든다. **개선:** 준비와 외부 요청을 나누고 자료 개수·대상·고유 ID를 확인한다. 전체 프레임워크를 추가하기 전에 작은 함수의 계약부터 분명히 한다.

원본 오류·수업용 단순화·목적에 따른 설계를 나눈다. 새 개선안은 당시 내 코드나 D 드라이브 수정본이 아니다.

## 7. 강사님 코드가 도움이 되는 비교



중복 인용 없이 양쪽에 같은 기준을 적용한다. 강사님의 호출 간격 조절은 목적을 참고하되 현재 제한의 증거로 쓰지 않는다. 내 문자열 id 읽기와 단순 목록 반환은 실제로 더 명확한 부분으로 인정한다. 양쪽의 같은 참조 문제는 모두 교정한다.

## 8. 결과를 추적하고 한 가지 바꾸기

| 입력 | 처리 | 반환 또는 오류 |
| --- | --- | --- |
|ID 1 한 건 | 새 작업 dict | 작업 1개 |
|ID 없음 | 필수값 확인 | ValueError |
|ID 1 두 건 | 중복 확인 | ValueError |
|빈 목록 | 반복 없음 | [] |

| 한 가지만 변경 | 확인 |
| --- | --- |
|ID 0 사용 | None이 아니므로 현재 예제는 허용 |
|ID를 빈 문자열로 | 현재 예제는 별도 금지하지 않음·계약 보완 필요 |
|source를 doc로 변경 | 원본과 같은 객체 |
|중복 검사 제거 | 같은 ID 작업이 두 번 생김 |

실패인데 빈 결과만 보이면 except와 반환 타입을 함께 읽는다. 작업마다 내용이 같아지면 참조 공유를 본다. import만 했는데 변경이 발생하면 파일 끝의 즉시 실행 줄을 확인한다. 실제 전송의 실패·재시도는 로컬 준비 함수의 성공과 별도로 기록한다.

**확인 범위:** 새 예제는 임시 폴더에서 Python 처리·요청 모양·고정 응답 가공을 확인한다. Elasticsearch나 AI 서비스의 실제 연결·적재·검색·임베딩·답변 성공을 재현한 것은 아니다. 원본 함수의 별도 검사도 외부 호출을 기록 대역으로 바꾼 범위이며 원본 파일과 패키지는 수정하지 않는다.
