## 1. 이 장에서 배울 것

문서·필드·인덱스·매핑을 구별한다. text와 keyword의 목적을 설명하고 JSON 읽기→actions 만들기→bulk 호출의 입력과 반환을 연결한다. 실제 접속 설정과 요청 준비, 적재 성공 확인을 서로 다른 단계로 읽는다.

## 2. 무엇이며, 왜 필요한가

### 문서는 검색할 한 건의 자료다

예를 들어 노트북 안내 한 건을 제목·분류·가격·내용으로 표현할 수 있다. 이 이름들이 필드이고, 필드와 값을 묶은 한 건이 문서다. JSON은 이 구조를 텍스트로 표현하는 형식이며 Python에서는 읽은 뒤 dict·list로 다룬다. 인덱스는 이런 문서를 모아 검색하는 단위다. 여기서는 computer라는 이름을 쓴다. SQL의 검색 성능을 위한 인덱스와 같은 뜻으로 외우지 않는다.

매핑은 각 필드를 어떤 종류로 처리할지 정한다. price가 숫자이면 크기를 비교할 수 있고 title이 text이면 분석한 용어를 검색에 사용할 수 있다. 문서에 문자열이 들어 있다는 사실만으로 모든 문자열 필드의 검색 방식이 같아지는 것은 아니다.

| 필드 종류 | 이 수업의 예 | 주로 읽을 의미 |
| --- | --- | --- |
| text | title·content | 문장을 분석해 용어로 색인·검색 |
| keyword | category | 정확한 범주값·집계·정렬 |
| integer / float | price / rating | 정수·소수 값 |
| date | created_at | 날짜 값 |
| dense_vector | 뒤 장의 embedding | 임베딩 숫자 목록·별도 기능 |

text의 분석은 문자 그대로 문장 전체를 보관해 부분 문자열을 찾는 것과 다르다. 분석기가 어떤 용어를 만들었는지가 중요하다. 동시에 이것을 의미 임베딩 벡터와 같은 처리라고 설명하면 안 된다. 양쪽 주석의 “text는 벡터로 분석”은 이 구분이 빠져 있어 교정한다.

### _id와 _source는 왜 따로 있을까?

_id는 인덱스 안에서 문서를 식별하는 메타데이터이고 _source는 문서 본문이다. 본문 안에도 id 필드가 있을 수 있지만 두 자리가 자동으로 같은 것은 아니다. 원본은 `_id: doc['id']`로 직접 연결했다. _index는 어느 인덱스에 보낼지 정한다. 세 항목을 묶은 작업을 actions에 쌓고 helpers.bulk로 여러 건을 보낸다.

클라이언트 객체를 만들었다고 서버에 인증·접속이 성공한 것은 아니다. 실제 요청의 응답이 있어야 한다. 또 bulk 호출이 반환한 성공 수·오류와 예외를 구별해야 한다. 기본 오류 설정에서는 실패 항목이 있으면 예외로 중단될 수 있으므로 “항상 errors 목록이 반환돼 다음 print가 실행된다”고 단정하지 않는다.

> 📚 **출처 · 본문 설명 확인:** [Elastic text](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/text) · [keyword](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/keyword) · [Python bulk helpers](https://www.elastic.co/docs/reference/elasticsearch/clients/python/client-helpers). 배운 의미 확인 근거다. 아래 표·전체 예제·풀이를 외부 문장 그대로 옮기지 않았다. 확인일: 2026-10-30.

## 3. 작은 예제로 먼저 이해하기

**새 설명 예제 · 필요한 파일 전체.** 같은 장의 폴더 구조를 유지한다. Python 표준 라이브러리만 쓴다. 아래 세 파일을 같은 폴더에 저장하고 `python example.py`를 실행한다. 실제 서버 없이 JSON 읽기와 전송할 작업의 모양을 확인하는 예제이며 적재 성공을 흉내 내어 출력하지 않는다.



**[documents.json](실습/책형_복습/01_연결과_문서적재/documents.json) — 새 예제 전체 파일**

```json
[{"id": 1, "title": "노트북 안내", "category": "laptop", "price": 900000}]
```

**[document_tools.py](실습/책형_복습/01_연결과_문서적재/document_tools.py) — 새 예제 전체 파일**

```python
import json
from pathlib import Path


def load_documents():
    path = Path(__file__).resolve().parent / 'documents.json'
    with path.open(encoding='utf-8') as file:
        return json.load(file)


def build_actions(documents):
    actions = []
    for doc in documents:
        actions.append({'_index': 'computer', '_id': doc['id'], '_source': doc})
    return actions
```

**[example.py](실습/책형_복습/01_연결과_문서적재/example.py) — 새 예제 전체 파일**

```python
from document_tools import load_documents, build_actions

mappings = {'properties': {
    'title': {'type': 'text'},
    'category': {'type': 'keyword'},
    'price': {'type': 'integer'},
}}
documents = load_documents()
actions = build_actions(documents)
print('문서 수:', len(documents))
print('대상·ID:', actions[0]['_index'], actions[0]['_id'])
print('본문 제목:', actions[0]['_source']['title'])
print('분류 타입:', mappings['properties']['category']['type'])
print('전송 여부:', False)
```

import한 load_documents의 전체 정의를 document_tools.py에 제공했다. __file__을 기준으로 같은 폴더의 JSON을 읽으므로 실행 작업 폴더와 파일 기준을 구별할 수 있다. build_actions는 받은 문서마다 전송할 dict를 만든다. mappings와 actions는 아직 Python 자료일 뿐이며 es.indices.create나 helpers.bulk를 호출하지 않았으므로 서버 상태를 변경하지 않았다.

**실행 결과:**

```text
문서 수: 1
대상·ID: computer 1
본문 제목: 노트북 안내
분류 타입: keyword
전송 여부: False
```

```python
def ingest_documents():
    documents = load_documents()

    actions = []

    for doc in documents :
        actions.append({
            '_index' : 'computer',
            '_id' : doc['id'], # '_id' : doc.get('id', None),
            '_source' : doc
        })

    success, errors = helpers.bulk(es, actions, stats_only=False) # stats_only=False 를 쓰면 성공/실패 값과 에러메시지를 돌려줌
    print('success : ', success)
    print('errors : ', len(errors), errors)

    return {
        'msg' : {
            'success' : success,
            'errors' : errors
        }
    }
```

**발췌 바로 풀이:** load_documents의 반환 목록을 반복해 각 작업의 대상·ID·본문을 묶는다. helpers.bulk는 실제 서버에 보내는 지점이다. stats_only=False는 오류 상세를 받는 형식과 관련되지만 기본 raise_on_error와 실패 시 예외도 함께 살펴야 한다. 코드만 읽고 성공 개수를 확정하지 않는다.

```python
def load_documents():
    print('__file__ : ', __file__) 

    BASE_DIR = Path(__file__).resolve().parents[0]
    DOCUMENT_FILE = BASE_DIR / 'data' / 'data.json' # 경로 합치기 Path의 경우 '/'로 +처럼 합침

    result = {}
    # with open('asdf', 'r') as file: # FileNotFoundError: [Errno 2] No such file or directory: 'asdf'
    try : # 혹시 파일이 없을경우 에러 발생 시 구동이 멈추지 않도록 try,except
        with open(DOCUMENT_FILE, 'r', encoding='UTF-8') as file: 
            # print(file) 

            # json을 dict로 변환해주는 lib
            result = json.load(file)
            # 참고로 dict를 json으로 변환 하려면 json.dump() 사용
            # print(result)
    except Exception as e :

    return result
```

**발췌 바로 풀이:** 경로는 util.py 기준 data/data.json이다. result를 빈 dict로 시작하고 파일 읽기 오류를 넓게 잡아 그대로 반환한다. 정상 입력은 문서 목록을 기대하는데 실패 시 dict가 되어 호출자가 빈 성공처럼 오해할 여지가 있다. 이 함수의 정의를 읽으면 ingest_documents에서 실제 어느 파일을 기대하는지 알 수 있다.

api.py는 FastAPI 앱에 es_router와 embedding_router를 연결하고 config.py는 환경변수에서 클라이언트 설정을 준비한다. 키의 이름·역할을 설명하는 것과 실제 값 공개는 다른 일이다. 이 교재는 접속키 값을 옮기지 않는다. util의 파일 경로로 읽은 문서가 es_router의 actions에 들어가고 bulk에 전달된다. run.py도 적재 함수를 파일 끝에서 바로 실행하므로 단순 import·실행을 읽기 검사와 같은 것으로 취급하지 않는다.

## 5. import·함수·입력·출력이 연결되는 흐름

`api.py의 라우터 등록 → es_router의 경로 함수 → util.load_documents() → data/data.json → actions → helpers.bulk(es, actions) → 성공 수/오류 또는 예외` 순서다. config의 es는 연결 대상과 인증 설정을 가진 클라이언트이고 actions는 전송 내용이다. 매핑 생성과 문서 적재는 다른 요청이다. 이 장의 새 예제는 파일 읽기와 작업 구성까지만 실행한다.

## 6. 잘한 점·아쉬운 점·개선 방향

**잘한 점:** 매핑을 명시하고 ID·본문을 작업 단위로 나누어 적었다. JSON 읽기를 util로 분리해 여러 함수에서 같은 입력을 사용할 수 있다. **아쉬운 점:** text를 벡터와 섞은 주석, 읽기 실패 시 반환 타입 변화, bulk가 항상 결과를 돌려준다는 기대는 복습 때 오해를 만든다. **개선:** 읽기 실패와 빈 목록을 구분하고 전송 전 입력·ID·작업 수를 확인한 뒤 실제 응답과 예외를 기록한다. 새 예제의 파일 오류는 숨기지 않고 호출자에게 드러나게 했다.

원본 오류·수업용 단순화·목적에 따른 설계를 나눈다. 새 개선안은 당시 내 코드나 D 드라이브 수정본이 아니다.

## 7. 강사님 코드가 도움이 되는 비교



매핑과 벌크의 핵심 동작은 양쪽이 같아 강사님 원문을 다시 붙이지 않는다. 두 주석의 text 설명에는 같은 교정이 필요하다. 코드의 출처가 아니라 실제 필드 종류와 호출 결과를 기준으로 판단한다.

## 8. 결과를 추적하고 한 가지 바꾸기

| 단계 | 값의 모양 | 실제 서버 변경 |
| --- | --- | --- |
|JSON 읽기 | 문서 dict의 목록 | 없음 |
|actions 만들기 | 메타데이터·본문 작업 목록 | 없음 |
|매핑 생성 호출 | 필드 정의 요청 | 성공 시 인덱스 생성 |
|bulk 호출 | 여러 적재 작업 | 성공 항목은 반영 가능 |
|반환 확인 | 성공/오류 또는 예외 | 전부 성공했는지 별도 판단 |

| 한 가지만 변경 | 예상 |
| --- | --- |
|새 JSON의 id 제거 | build_actions에서 KeyError |
|문서를 두 건으로 | 전송하지 않은 작업 2개 |
|category의 타입을 text로 | 설정 의미가 달라짐·서버 분석은 이 예제에서 미확인 |
|실제 원본에서 같은 ID 재전송 | 같은 식별 문서에 영향 가능·새 문서만 늘어난다고 가정하지 않음 |

파일 오류는 실제 JSON 위치를 먼저 본다. json.load 오류는 JSON 문법과 인코딩을 확인한다. 서버 연결·권한·중복 인덱스 오류는 파일 읽기 성공과 별개다. bulk 도중 실패했다면 성공 항목까지 모두 되돌아갔다고 가정하지 말고 개별 결과와 예외를 확인한다.

**확인 범위:** 새 예제는 임시 폴더에서 Python 처리·요청 모양·고정 응답 가공을 확인한다. Elasticsearch나 AI 서비스의 실제 연결·적재·검색·임베딩·답변 성공을 재현한 것은 아니다. 원본 함수의 별도 검사도 외부 호출을 기록 대역으로 바꾼 범위이며 원본 파일과 패키지는 수정하지 않는다.
