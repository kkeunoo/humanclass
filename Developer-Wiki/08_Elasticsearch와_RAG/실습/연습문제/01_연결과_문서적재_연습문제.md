# 01. Elasticsearch — 문서·인덱스·매핑과 적재 요청을 연결하기 — 연습문제

[본문](../../01_연결과_문서적재.md) · [문제 목차](README.md)

실제 수업 내용을 바탕으로 **새로 구성한 연습문제**다. 원본·당시 내 코드·새 개선안을 구별한다. 예상 → 이유 → 한 가지 변경 순서로 푼다.

## 목표와 준비

문서·필드·인덱스·매핑을 구별한다. text와 keyword의 목적을 설명하고 JSON 읽기→actions 만들기→bulk 호출의 입력과 반환을 연결한다. 실제 접속 설정과 요청 준비, 적재 성공 확인을 서로 다른 단계로 읽는다.

[본문 3절](../../01_연결과_문서적재.md#example)의 폴더·설치·입력·실행 조건부터 확인한다. 아래 필요한 파일 전체를 같은 구조로 저장한다. 가져오는 함수·모델 정의도 빠뜨리지 않는다.

## 문제 1. 실행 결과 예상

**documents.json**

```json
[{"id": 1, "title": "노트북 안내", "category": "laptop", "price": 900000}]
```

**document_tools.py**

```python
import json
from pathlib import Path


def load_documents():
    path = Path(__file__).resolve().parent / 'documents.json'
    with path.open(encoding='utf-8') as file:
        return json.load(file)


def build_actions(documents):
    actions = []
    for doc in documents:
        actions.append({'_index': 'computer', '_id': doc['id'], '_source': doc})
    return actions
```

**example.py**

```python
from document_tools import load_documents, build_actions

mappings = {'properties': {
    'title': {'type': 'text'},
    'category': {'type': 'keyword'},
    'price': {'type': 'integer'},
}}
documents = load_documents()
actions = build_actions(documents)
print('문서 수:', len(documents))
print('대상·ID:', actions[0]['_index'], actions[0]['_id'])
print('본문 제목:', actions[0]['_source']['title'])
print('분류 타입:', mappings['properties']['category']['type'])
print('전송 여부:', False)
```

실행 전에 결과를 먼저 적는다. 자료의 모양·분류 결과·확률·점수·현재 변수의 대상을 구별한다.

<details>
<summary>풀이</summary>

```text
문서 수: 1
대상·ID: computer 1
본문 제목: 노트북 안내
분류 타입: keyword
전송 여부: False
```

import한 load_documents의 전체 정의를 document_tools.py에 제공했다. __file__을 기준으로 같은 폴더의 JSON을 읽으므로 실행 작업 폴더와 파일 기준을 구별할 수 있다. build_actions는 받은 문서마다 전송할 dict를 만든다. mappings와 actions는 아직 Python 자료일 뿐이며 es.indices.create나 helpers.bulk를 호출하지 않았으므로 서버 상태를 변경하지 않았다.

| 단계 | 값의 모양 | 실제 서버 변경 |
| --- | --- | --- |
|JSON 읽기 | 문서 dict의 목록 | 없음 |
|actions 만들기 | 메타데이터·본문 작업 목록 | 없음 |
|매핑 생성 호출 | 필드 정의 요청 | 성공 시 인덱스 생성 |
|bulk 호출 | 여러 적재 작업 | 성공 항목은 반영 가능 |
|반환 확인 | 성공/오류 또는 예외 | 전부 성공했는지 별도 판단 |

</details>

## 문제 2. 이유 설명

1. _id와 본문 id가 자동으로 같은가?
2. text를 임베딩 벡터라고 불러도 되는가?
3. 새 예제의 문서 수 1은 서버 적재 성공 1을 뜻하는가?

<details>
<summary>풀이</summary>

1. 아니다. 원본이 직접 doc의 id를 _id에 넣었다.
2. 이 실습에서는 단어 분석 필드와 별도의 dense_vector 필드를 구별한다.
3. 로컬 JSON에서 읽어 만든 작업 한 개이며 전송하지 않았다.

</details>

## 문제 3. 한 가지만 바꾸기

| 한 가지만 변경 | 예상 |
| --- | --- |
|새 JSON의 id 제거 | build_actions에서 KeyError |
|문서를 두 건으로 | 전송하지 않은 작업 2개 |
|category의 타입을 text로 | 설정 의미가 달라짐·서버 분석은 이 예제에서 미확인 |
|실제 원본에서 같은 ID 재전송 | 같은 식별 문서에 영향 가능·새 문서만 늘어난다고 가정하지 않음 |

<details>
<summary>막힐 때 확인</summary>

파일 오류는 실제 JSON 위치를 먼저 본다. json.load 오류는 JSON 문법과 인코딩을 확인한다. 서버 연결·권한·중복 인덱스 오류는 파일 읽기 성공과 별개다. bulk 도중 실패했다면 성공 항목까지 모두 되돌아갔다고 가정하지 말고 개별 결과와 예외를 확인한다.

</details>

## 채점과 복습

정상 출력뿐 아니라 입력 열·정답·분할·평가 대상의 차이도 설명한다. 새 예제는 독립 실행이며 실제 검색·AI 서비스 성공과 구별한다. TIP 확장은 필수 조건이 아니다. 정의→입력→호출→반환→다음 평가의 흐름을 연결한다.
