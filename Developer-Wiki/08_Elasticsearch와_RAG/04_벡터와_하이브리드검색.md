# 04. 벡터·하이브리드 검색 — 가까운 결과를 찾고 순위로 합치기

[Elasticsearch·RAG 목차](README.md) · [읽기 안내](00_검색과_RAG_읽기안내.md)

벡터 검색은 가까운 청크를 찾고, 하이브리드 검색은 다른 방식으로 찾은 목록을 합친다. 여기서는 서버가 만든 원점수를 섞는 대신 순위를 점수로 바꾸는 실제 RRF 계산을 작은 두 목록으로 끝까지 따라간다.

## 1. 이 장에서 배울 것

질문 벡터와 저장 벡터의 관계, k·num_candidates·size의 차이를 설명한다. 같은 _id의 순위 기여를 누적하고 정렬·잘라내기·formatter 반환까지 연결한다. 고정 순위 예제와 실제 벡터 유사도 검색을 구별한다.

## 2. 무엇이며, 왜 필요한가

### 벡터 검색은 분류 답을 고르는 kNN 실습과 다르다

질문도 문서와 비교할 수 있는 숫자 표현으로 바꾼 뒤 저장 embedding과 가까운 자료를 찾는다. 이 호출의 결과는 청크 목록이다. 앞 머신러닝 단원의 0·1 정답을 다수결로 고르는 설명과 섞지 않는다. 유사한 청크가 찾는 질문의 정답을 실제로 담고 있는지는 다음에 본문을 읽어 확인해야 한다.

원본 size=5일 때 query_vector는 질문의 숫자 목록, field는 embedding, k는 선택할 가까운 결과 수다. num_candidates=max(5*10,50)은 50으로 계산되지만 실제 문서가 부족해도 후보 50개가 반드시 존재한다는 뜻은 아니다. 근사 kNN의 샤드별 후보 검토 설정이며, 최종 반환 목록 길이와 같은 수가 아니다. size도 응답에 반환할 hit 수를 정하는 별도 설정이다.

| 자리 | 원본 값의 예 | 구별 |
| --- | --- | --- |
| query_vector | 질문 임베딩 | 문서 본문이 아님 |
| field | embedding | 저장 벡터 필드 |
| k | 5 | 가까운 결과 선택 수 |
| num_candidates | 50 | 후보 검토 설정 |
| size | 5 | 반환할 hit 수 설정 |

### 서로 다른 검색 점수를 더하면 왜 곤란할까?

문자 검색의 관련도와 벡터 검색의 유사도는 계산과 크기가 다를 수 있다. 원본은 “점수 5와 0.9를 그대로 더하기”보다 각 목록에서의 순위를 사용한다. RRF는 한 목록에서 순위 r인 자료에 `1 / (60 + r)`을 더하는 방식이다. 두 목록에 같은 _id가 있으면 두 번 더한다.

아래 새 예제에서 문자 순위는 A·B, 벡터 순위는 B·C다. A는 1/61, B는 1/62 + 1/61, C는 1/62다. 따라서 B·A·C 순서다. 이 계산은 질문의 답이 맞는지, 확률이 몇 퍼센트인지 계산한 것이 아니다. 다른 검색의 순위를 한 순서로 합친 결과다.

### 합칠 때 무엇을 같은 자료로 볼까?

원본은 hit의 _id를 사용한다. 청크 7-0과 7-1은 같은 원본 문서에 속해도 다른 청크 ID라 따로 계산된다. 반대로 두 목록의 _id가 같으면 본문을 한 개 보관하고 score를 누적한다. 두 검색이 같은 청크 집합과 일관된 ID를 사용한다는 전제가 중요하다. 총 고유 청크 수와 상위 몇 개만 반환하는 수도 구분한다.

## 3. 작은 예제로 먼저 이해하기

**새 설명 예제 · 필요한 파일 전체.** 같은 장의 폴더 구조를 유지한다. Python만 사용한다. 두 파일을 같은 폴더에 저장하고 `python example.py`를 실행한다. 문자·벡터 검색을 실행하지 않고 이미 정해 둔 두 결과 목록으로 순위 합산만 확인한다. 이 입력의 순위는 이해용 가상 자료다.



**[rank_tools.py](실습/책형_복습/04_벡터와_하이브리드검색/rank_tools.py) — 새 예제 전체 파일**

```python
def fuse(text_hits, vector_hits, rank_constant=60, size=10):
    scores = {}
    for hits in [text_hits, vector_hits]:
        for rank, hit in enumerate(hits, start=1):
            doc_id = hit['_id']
            if doc_id not in scores:
                scores[doc_id] = {'score': 0.0, 'source': hit['_source']}
            scores[doc_id]['score'] += 1 / (rank_constant + rank)
    ordered = sorted(scores.items(), key=lambda item: item[1]['score'], reverse=True)
    results = []
    for doc_id, data in ordered[:size]:
        results.append({'id': doc_id, 'document': data['source'], 'score': data['score']})
    return {'results': results, 'total': len(scores)}
```

**[example.py](실습/책형_복습/04_벡터와_하이브리드검색/example.py) — 새 예제 전체 파일**

```python
from rank_tools import fuse

text_hits = [
    {'_id': 'A', '_source': {'title': 'A 안내'}},
    {'_id': 'B', '_source': {'title': 'B 안내'}},
]
vector_hits = [
    {'_id': 'B', '_source': {'title': 'B 안내'}},
    {'_id': 'C', '_source': {'title': 'C 안내'}},
]
result = fuse(text_hits, vector_hits)
print('순서:', [row['id'] for row in result['results']])
print('점수:', [round(row['score'], 6) for row in result['results']])
print('고유 결과:', result['total'])
short = fuse(text_hits, vector_hits, size=1)
print('상위 1개·총수:', len(short['results']), short['total'])
print('빈 입력:', fuse([], []))
```

fuse의 전체 정의에서 두 목록을 같은 규칙으로 반복한다. 같은 B의 score가 누적되고 sorted가 내림차순으로 정렬한다. size=1이어도 고유 후보는 세 개이므로 total은 3이다. 원본 formatter는 청크 _id를 최종 결과에서 생략하지만, 새 예제는 순위 계산을 확인하기 위해 id를 함께 남긴 개선안이다.

**실행 결과:**

```text

점수: [0.032522, 0.016393, 0.016129]
고유 결과: 3
상위 1개·총수: 1 3
빈 입력: {'results': [], 'total': 0}
```

def get_keyword_embedding_with_llm(keyword):

        query: {keyword}

    result = gemini.models.embed_content(
        model='gemini-embedding-2',

## 6. 잘한 점·아쉬운 점·개선 방향

**잘한 점:** 다른 검색의 원점수를 무작정 더하지 않고 ID별 순위 기여를 누적했다. **아쉬운 점:** 후보 수와 반환 수, 최종 total의 범위가 주석만으로는 흐려질 수 있다. formatter에서 _id를 잃으면 청크 출처 추적도 불편하다. **개선:** 계산 입력의 범위와 total 의미를 적고 확인용 ID를 보존한다. 두 검색이 같은 ID의 다른 본문을 돌려줄 때 어떤 본문을 선택할지도 정하면 좋다.

원본 오류·수업용 단순화·목적에 따른 설계를 나눈다. 새 개선안은 당시 내 코드나 D 드라이브 수정본이 아니다.

## 8. 결과를 추적하고 한 가지 바꾸기

| ID | 문자 순위 기여 | 벡터 순위 기여 | 합계·순서 |
| --- | --- | --- | --- |
|A | 1/61 | 없음 | 약 0.016393·2위 |
|B | 1/62 | 1/61 | 약 0.032522·1위 |
|C | 없음 | 1/62 | 약 0.016129·3위 |

| 한 가지만 변경 | 예상 |
| --- | --- |
|두 목록 모두 B를 1위로 | B에 1/61 두 번 |
|벡터 목록을 비움 | 문자 순위만 사용 |
|size를 1로 | 반환 1개·고유 총수 3 |
|원점수만 바꿈 | 새 fuse는 순위만 써 결과 동일 |
|같은 점수 발생 | 현재 정렬은 삽입 순서에 기대므로 명시 정책 검토 |

같은 자료가 합쳐지지 않으면 _id 형식과 청크 ID를 본다. 결과가 적으면 인덱스 자료·후보 수·반환 수를 구별한다. 벡터 검색 오류는 질문과 저장의 차원·모델·필드 종류를 확인한다. RRF 숫자를 0~1 확률로 읽거나 머신러닝 시험 점수처럼 비교하지 않는다.

**확인 범위:** 새 예제는 임시 폴더에서 Python 처리·요청 모양·고정 응답 가공을 확인한다. Elasticsearch나 AI 서비스의 실제 연결·적재·검색·임베딩·답변 성공을 재현한 것은 아니다. 원본 함수의 별도 검사도 외부 호출을 기록 대역으로 바꾼 범위이며 원본 파일과 패키지는 수정하지 않는다.

<a id="tips"></a>

## 9. 추가로 알면 좋은 것과 출처

> 💡 **TIP · 수업 범위 밖:** 후보 수·상수 변경의 품질 평가, 검색 평가용 질문 집합, 재순위 모델, 서버 제공 RRF 기능의 배포별 지원은 추가 학습이다. 기존 라이선스 메모는 당시 기록이며 현재 사용 환경의 지원 여부는 별도 확인해야 한다.

확인한 라이브러리 의미와 수업 밖 확장을 구분한다. 위 출처는 본문의 설명 근거이며 TIP에 적힌 새 주제를 이미 배운 것으로 간주하지 않는다.
