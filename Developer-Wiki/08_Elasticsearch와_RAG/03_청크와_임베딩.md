## 1. 이 장에서 배울 것

청크·겹침·임베딩·차원을 구별한다. split_text의 전체 흐름과 import한 함수 정의를 읽고, 문자 수 30이 모든 결과의 상한이 아닌 이유를 설명한다. 청크마다 다른 본문·벡터·ID가 저장되도록 필요한 조건을 이해한다.

## 2. 무엇이며, 왜 필요한가

### 왜 긴 글을 조각으로 만들까?

검색 결과가 책 전체 한 권이라면 필요한 설명을 찾고 답에 넣기가 어렵다. 청크는 검색·답변에 사용할 작은 텍스트 조각이다. 문서의 일부를 찾을 수 있게 하고, 질문과 관련된 부분을 문맥으로 보내려는 목적이 있다. 나누기만 하면 늘 더 좋아지는 것은 아니며 너무 잘게 나누면 설명이 끊길 수 있다.

수업 코드는 문장부호 뒤 공백에서 먼저 나누고 여러 문장을 약 30글자까지 묶는다. 문장 하나가 30글자보다 길면 그 문장을 그대로 둔다. 그 다음 앞 청크의 마지막 6글자를 다음 청크 앞에 붙인다. 따라서 **문장 묶기 기준 30**과 **겹침 뒤 최종 길이**는 다르다. 토큰 30개를 세는 코드도 아니다.

| 말 | 무엇인가 | 원본에서 확인 |
| --- | --- | --- |
| 문장 분리 | 특정 경계에서 문자열 나누기 | re.split |
| 청크 묶기 | 문장을 합쳐 조각 만들기 | temp·candidate·chunks |
| overlap | 앞 조각 끝을 다음 앞에 겹침 | before[-6:] |
| embedding | 텍스트를 숫자 목록으로 표현 | 외부 embed_content 호출 |
| dims | 저장할 숫자 개수 | dense_vector의 384 |

### 숫자 목록은 답변 문장이 아니다

임베딩은 비교에 사용할 숫자 표현이다. 비슷한 의미를 찾는 데 쓰지만 숫자 한 개가 한국어 특정 단어의 뜻이라고 읽는 방식은 아니다. 저장할 문서와 검색 질문을 호환되는 임베딩 공간으로 표현해야 비교할 수 있다. 길이만 같다고 서로 다른 모델의 결과가 자동으로 호환되지는 않는다.

원본은 제목·내용을 문장으로 묶어 Gemini 임베딩에 보내고 반환의 첫 embedding.values를 꺼낸다. 요청의 output_dimensionality=384와 매핑 dims=384가 맞아야 한다. 숫자 개수는 CPU의 배수라는 이유만으로 임의 선택하는 것이 아니라 모델·서비스·저장 설정의 지원을 함께 봐야 한다. “256이면 뉘앙스가 약하다”도 모든 모델에 적용되는 규칙은 아니다.

### 같은 dict에 붙인 두 이름은 두 문서가 아니다

`doc2 = doc`은 복사가 아니라 같은 객체를 가리키는 이름을 하나 더 만든다. actions에 _source로 그 객체를 넣은 뒤 다음 반복에서 doc2의 청크 번호·벡터를 바꾸면 앞 작업의 본문도 바뀔 수 있다. _id 문자열은 당시 계산한 값을 담고 _source는 공유 dict를 담으므로 서로 다른 청크 ID인데 내용은 마지막 청크 상태가 되는 문제가 생긴다. 각 청크의 별도 dict와 실제 chunk 본문을 함께 준비하는 개선이 필요하다.

> 📚 **출처 · 본문 설명 확인:** [Elastic dense_vector](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/dense-vector) · [Gemini 임베딩](https://ai.google.dev/gemini-api/docs/embeddings) · [Python re.split](https://docs.python.org/ko/3/library/re.html#re.split). 배운 의미 확인 근거다. 아래 표·전체 예제·풀이를 외부 문장 그대로 옮기지 않았다. 확인일: 2026-10-30.

## 3. 작은 예제로 먼저 이해하기

**새 설명 예제 · 필요한 파일 전체.** 같은 장의 폴더 구조를 유지한다. Python 표준 라이브러리만 쓴다. 아래 두 파일을 같은 폴더에 저장하고 `python example.py`를 실행한다. fixed_embedding은 미리 정한 숫자를 돌려주는 대역이며 실제 임베딩 모델이 아니다. 2차원 숫자는 구조를 보기 위한 가상 값으로, 원본 384차원 서버 매핑에 적재하지 않는다.



**[chunk_tools.py](실습/책형_복습/03_청크와_임베딩/chunk_tools.py) — 새 예제 전체 파일**

```python
import re


def split_text(text, chunk_size=30, overlap_size=6):
    sentences = re.split(r'(?<=[.!?])\s+', text.strip())
    sentences = [s.strip() for s in sentences if s.strip()]
    chunks = []
    temp = ''
    for sentence in sentences:
        candidate = f'{temp} {sentence}' if temp else sentence
        if len(candidate) <= chunk_size:
            temp = candidate
        else:
            if temp:
                chunks.append(temp)
            temp = sentence
    if temp:
        chunks.append(temp)
    overlap_chunks = []
    for index, chunk in enumerate(chunks):
        if index == 0:
            overlap_chunks.append(chunk)
        else:
            prefix = chunks[index - 1][-overlap_size:] if overlap_size > 0 else ''
            overlap_chunks.append(f'{prefix} {chunk}'.strip())
    return overlap_chunks


def build_actions(doc, embed):
    actions = []
    for index, chunk in enumerate(split_text(doc['content'])):
        vector = embed(doc['title'], chunk)
        source = {**doc, 'content': chunk, 'chunk_index': index, 'embedding': vector}
        actions.append({'_index': 'computer_chunk', '_id': f'{doc["id"]}-{index}', '_source': source})
    return actions
```

```python
def get_embedding_with_llm(title, content):
    prompt = f'''
        task: retrival document\n
        title: {title}\n
        content: {content}
'''

    result = gemini.models.embed_content(
        model='gemini-embedding-2',
        # 텍스트를 임베딩한다
        contents=[
            types.Content(parts=[
                types.Part.from_text(text=prompt)
            ])
        ],
        #옵션
        config=types.EmbedContentConfig(
            output_dimensionality=384
        )
    )

    return result.embeddings[0].values
```

**발췌 바로 풀이:** 제목·청크를 prompt에 넣고 embed_content의 응답에서 첫 숫자 목록을 반환한다. model 문자열과 output_dimensionality는 요청 설정이며 실제 성공·차원은 응답을 확인해야 한다. task라는 문구를 prompt에 넣은 것과 API의 별도 task_type 옵션을 설정한 것은 같은 일이 아니다.

## 5. import·함수·입력·출력이 연결되는 흐름

## 6. 잘한 점·아쉬운 점·개선 방향

**잘한 점:** 긴 글을 문장으로 나누고 겹침·청크 번호·원본문서 ID를 함께 다뤘다. **아쉬운 점:** 같은 dict를 재사용하고 저장 content를 바꾸지 않아 청크별 저장이 의도와 어긋날 수 있다. **개선:** 새 dict를 만들고 chunk를 content에 담으며 전송 전 작업별 본문·벡터·ID를 검사한다. 가상 차원 값이나 호출 대기를 실제 서비스의 품질·제한 보장으로 설명하지 않는다.

원본 오류·수업용 단순화·목적에 따른 설계를 나눈다. 새 개선안은 당시 내 코드나 D 드라이브 수정본이 아니다.

|source를 doc로 직접 지정 | 여러 작업이 같은 dict를 가리킬 수 있음 |
|차원이 다른 벡터 전송 | 실제 저장 설정과 불일치·이 예제에서는 전송하지 않음 |

청크가 예상보다 길면 긴 단일 문장과 겹침을 확인한다. 앞선 작업의 값이 바뀌면 객체 참조를 살핀다. 적재한 본문과 질문응답의 인용이 어긋나면 chunk와 전체 content 중 무엇을 저장했는지 본다. 임베딩 오류는 모델·입력·차원·응답 존재를 단계별로 구분한다.

**확인 범위:** 새 예제는 임시 폴더에서 Python 처리·요청 모양·고정 응답 가공을 확인한다. Elasticsearch나 AI 서비스의 실제 연결·적재·검색·임베딩·답변 성공을 재현한 것은 아니다. 원본 함수의 별도 검사도 외부 호출을 기록 대역으로 바꾼 범위이며 원본 파일과 패키지는 수정하지 않는다.

<a id="tips"></a>

## 9. 추가로 알면 좋은 것과 출처

> 💡 **TIP · 수업 범위 밖:** 토큰 기준 청킹·고급 정규식·문서 구조 기반 분할·차원 축소·임베딩 모델 비교·재시도 정책은 추가 학습이다. 현재 본문은 실제 문자 기준 알고리즘과 참조 결함, 청크와 저장 본문의 일치를 읽는 데 집중한다.

확인한 라이브러리 의미와 수업 밖 확장을 구분한다. 위 출처는 본문의 설명 근거이며 TIP에 적힌 새 주제를 이미 배운 것으로 간주하지 않는다.

<a id="practice"></a>

## 10. 복습과 빠른 정리

1. 원본의 chunk_size=30은 최종 길이 상한인가?
2. doc2=doc 뒤 이전 작업도 바뀌는 이유는?
3. 차원이 같으면 모든 임베딩 모델을 섞어도 되는가?

<details>
<summary>풀이 — 먼저 결과와 이유를 적은 뒤 펼치기</summary>

1. 긴 한 문장과 겹침 때문에 아니다.
2. 별도 복사가 아니라 같은 dict 참조를 저장했기 때문이다.
3. 숫자 개수뿐 아니라 호환되는 모델·표현 공간이 필요하다.

</details>
