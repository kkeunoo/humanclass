# 00-02. 오류 읽기 — 마지막 줄과 멈춘 위치에서 시작하기

[Python 목차](README.md) · [읽기 안내](00-00_Python_V3_동작_백과_읽기법.md)

오류 화면은 공부가 실패했다는 표시가 아니라 실행을 이어 갈 수 없었던 위치와 이유를 담은 정보다. 먼저 메시지를 읽는 습관을 익히고, 함수·조건·예외 처리의 상세 문법은 뒤 장에서 다시 연결한다.

## 1. 이 장에서 배울 것

문법을 읽는 단계의 오류와 실행 중 예외를 구분한다. 출력이 생기기 전에 실패할 수 있음을 확인하고, 오류 종류·파일·줄·실제 값 순서로 원인을 좁힌다.

실제 원본·새 예제·개선안·선택 학습을 구분하고 입력·실행 순서·반환값·출력을 연결한다.

<a id="concepts"></a>

## 2. 무엇이며, 왜 필요한가

문법 오류는 Python이 문장을 올바른 구조로 읽을 수 없는 경우다. 실행 중 예외는 문장 모양을 읽을 수 있어도 그 값으로 작업하다 문제가 생긴 경우다. 따옴표나 괄호를 닫지 않은 코드와 10/0은 실패하는 지점이 다르다.

| 읽을 정보 | 뜻 | 확인 방법 |
| --- | --- | --- |
| 오류 종류 | 어떤 성격의 실패인가? | 마지막 줄의 이름 |
| 설명 | 무엇이 허용되지 않았나? | 이름 뒤의 메시지 |
| 파일·줄 | 어디를 실행하다 멈췄나? | Traceback의 호출 경로 |
| 그 줄의 값 | 왜 그 작업이 안 됐나? | 변수와 입력을 되짚기 |

ZeroDivisionError는 0으로 나누려 했다는 뜻이다. print(10/0)도 print 함수에 결과를 넘기기 전에 10/0을 계산하다 실패한다. 따라서 숫자 결과를 출력한 다음 오류가 난 것이 아니다. 처리하지 않은 예외가 생기면 그 실행 흐름의 다음 줄은 진행하지 않는다.

오류 이름만 보고 고치는 줄을 찍지 않는다. 같은 예외라도 입력이 잘못됐는지, 계산식이 잘못됐는지, 분기에서 값을 만들지 않았는지 원인이 다를 수 있다. Python 버전에 따라 메시지의 화살표·문구 모양은 달라질 수 있다.

> 📚 **출처 · 본문 설명 확인:** [Python 공식 문서: 문법 오류와 예외](https://docs.python.org/ko/3/tutorial/errors.html). 실제 배운 문법의 의미를 확인한 근거다. 예제·표·풀이 자체는 수업 자료를 바탕으로 새로 구성했다. 외부 문장을 직접 인용하지 않았다. 이번 문법 확인 기간: 2026-10-28~29.

## 3. 작은 예제로 먼저 이해하기

**새 설명 예제 · 전체 코드.** [실행 파일](실습/책형_복습/00-02_Python_오류와_예외.py)을 제공한다. Python이 설치된 환경에서 새 .py 파일로 저장해 실행한다. 터미널은 그 파일이 있는 폴더에서 열고 `python 파일이름.py`를 실행한다. VS Code의 Python 실행 기능을 사용해도 된다. 결과는 터미널에 표시된다.



```python
print('시작')
print(10 / 0)
print('끝')
```

의도적으로 예외를 관찰하는 전체 예제다. 시작은 출력되지만 두 번째 줄의 나눗셈에서 실패하여 끝은 출력되지 않는다. 아래 관찰에는 핵심 오류 마지막 줄만 적었으며 실제 화면에는 파일 경로와 줄 번호도 보인다. 오류를 없애기 전에 어느 작업까지 진행했는지 설명해 본다.

**예상 출력 또는 관찰:**

```text
시작
ZeroDivisionError: division by zero
(중간의 파일·줄 경로는 환경에 따라 다르며 끝은 출력되지 않음)
```

## 4. 내가 작성한 코드를 따라 읽기

아래는 원본 발췌다. 주석의 잘못된 설명도 원문을 보존하고 풀이에서 교정한다. 필요한 선언·호출·다른 파일의 정의는 다음 절까지 연결해 읽는다.

### 내 코드 — 원본 발췌

출처: `D:/workspace/workspace_python/14_try.py` 1–7행

```python
# try, except 사용 전 방법 1
def div(x, y) :
    if y != 0 :
        result = x / y
    else :
        print('두 번째 숫자는 0이 올 수 없습니다')
    return result
```

**발췌 바로 풀이:** 이 함수는 정의만으로 나눗셈을 실행하지 않는다. 뒤에서 div(7, 0)처럼 호출하면 안내를 출력한 뒤, 값이 없는 result를 반환하려다 별도 예외가 난다. 함수와 반환은 11장, 예외 처리는 14장에서 자세히 다시 읽는다.

수업 뒤쪽의 div는 y가 0이 아닐 때만 나누는 함수다. 지금은 상세 함수 문법을 외우기보다 “어떤 갈래에서 값을 만들었는가”를 읽는 예고로 본다. 내 코드는 y가 0이면 안내만 출력하고 result를 만들지 않은 채 return result에 도달한다. 그래서 0으로 나누기는 막았지만 UnboundLocalError라는 다른 예외가 난다. result가 함수 안의 모든 실행 경로에서 준비되지 않았기 때문이다.

<a id="connections"></a>

## 5. 선언·호출·파일이 연결되는 흐름

div 정의 → div(7, 0) 호출 → x=7·y=0으로 함수 안 진행 → y!=0 조건은 거짓 → 안내 출력 → return result 읽기 → 값이 없어 예외 발생 순서다. 이 예외는 x/y 줄을 실행한 결과가 아니다. 앞서 들여쓴 # 주석도 실제 문장이 아니므로 현재 오류의 원인으로 섞지 않는다. 예외별 except·else·finally의 전체 정의와 호출은 14장 본문에 있다.

<a id="review"></a>

## 6. 잘한 점·아쉬운 점·개선 방향

**잘한 점:** 내 함수는 분모를 미리 검사하여 나눗셈 조건을 생각했다. **실제 오류:** 실패 갈래에서도 반환에 필요한 result가 준비되어 있어야 한다. **개선 선택:** 강사님처럼 먼저 초기값을 두거나 실패 갈래의 반환 정책을 명시할 수 있다. 다만 실패를 숫자 0으로 돌려주는 선택은 정상 계산 0과 구분이 어려운 한계도 있다. 지금은 오류를 숨기기보다 함수의 계약을 확인하는 질문으로 남긴다.

개선안은 D 드라이브 원본을 수정한 결과가 아니다. 실제 오류·수업용 단순화·목적에 따른 선택을 구별한다.

## 7. 강사님 코드가 도움이 되는 비교

출처: `D:/workspace_teacher/workspace_python/_14_try.py` 2–8행

```python
def div(x, y):
    result = 0
    if y != 0 :
        result = x / y
    else :
        print('두번째 숫자는 0이 올 수 없습니다')
    return result
```

강사님은 result=0을 먼저 만들어 div(7, 0)에서 안내 뒤 0을 반환한다. 내 코드는 그 초기화가 없어 같은 입력에서 결과가 다르므로 필요한 함수만 인용한다. 강사님 코드가 현재 예외는 피하지만 모든 상황에서 0 반환이 좋은 정책이라고 일반화하지 않는다.

<a id="results"></a>

## 8. 결과를 추적하고 한 가지 바꾸기

| 호출 | 나눗셈 수행 | 내 result | 결과 |
| --- | --- | --- | --- |
| div(7, 2) | 수행 | 3.5 | 3.5 반환 |
| div(7, 0) | 안 함 | 준비 안 됨 | 안내 뒤 UnboundLocalError |
| 강사님 div(7, 0) | 안 함 | 초기값 0 | 안내 뒤 0 반환 |

본격적인 except 갈래·else·finally와 return의 관계는 [14-01](14-01_Python_예외처리_심화.md)에서 읽는다. 이 시작 장은 그 전체를 선행 암기하는 곳이 아니라, 이후 오류가 났을 때 돌아올 읽기 기준이다.

| 한 가지만 변경 | 예상 | 이유 |
| --- | --- | --- |
| 작은 예제 분모를 2로 | 시작·5.0·끝 | 나눗셈이 성공 |
| 작은 예제 둘째 줄을 주석 처리 | 시작·끝 | 해당 계산 미실행 |
| 내 div의 첫 줄에 result=0 | 0 입력 때 안내 뒤 0 | 반환할 값이 준비됨 |

오류 마지막 줄과 해당 파일·줄부터 본다. 주석 속 오류 예시를 실제 실행 결과로 읽지 않는다. 예외가 두려워 모든 줄을 없애기보다 한 입력만 바꿔 실패 조건을 좁힌다. 함수 안 result 문제는 전역 이름을 임의로 추가하기보다 그 함수의 각 갈래를 확인한다.
